第 12 课 ⏱ 约 22 分钟

系统化阅读与调试脚本

先建立执行模型，再沿输入、状态变化、外部边界和失败路径验证行为

前 11 课覆盖了脚本运行、数据传递、失败处理和外部调用。本课把这些知识用于阅读现有脚本：先建立结构和主路径，再核实陌生语义，并用最小用例验证失败路径。

1. 阅读策略：四遍法

大多数人的问题是"从第 1 行开始逐行读"。这就像读一本小说时先查每个生词——你迷失在细节里，忘了故事在讲什么。

  第一遍（快速）  扫结构——这个脚本有几"块"？骨架长什么样？
  第二遍（主干）  追路径——main() 从头到尾走了什么路径？
  第三遍（定点）  查细节——关键命令的参数含义、变量的来源
  第四遍（按需）  调试验证——特定行为有疑问时构造受控实验

2. 第一遍：扫结构——认出骨架模式

第一遍先不进入函数实现，只读结构。优先识别这些信号：

# 打开脚本，第一眼扫什么？

#!/bin/bash                              # ← Shebang：是什么解释器？bash 还是 sh？
# deploy.sh — 部署脚本                     ← 文件头注释：它是干什么的？
set -euo pipefail                        # ← 选择了哪些失败规则？例外是否被正确处理？

readonly APP_NAME="myapp"                # ← 全局常量区：有哪些配置值？
readonly LOG_DIR="/var/log/${APP_NAME}"

log() { ... }                            # ← 工具函数区：日志、错误处理的"基础设施"
die() { ... }

check_prereqs() { ... }                  # ← 业务函数区：这是脚本真正的"动词"
backup() { ... }
deploy() { ... }

main() {                                 # ← 主入口：脚本的"目录"
    check_prereqs
    backup
    deploy "$@"
}
main "$@"                                # ← 启动：参数怎么传进 main
第一遍的核心产出：你能用一句话概括脚本结构——"这是一个部署脚本，有前置检查和备份，主逻辑在 deploy()，入口是 main "$@"，开了严格模式"。如果一句话说不清，说明你对脚本的骨架理解还不够。

3. 第二遍：追主干——画出执行路径

从 main "$@" 开始，顺着函数调用链往下追，不进入函数的实现细节：

main "$@"
│
├── load_config          # 加载配置（从哪里？环境变量？配置文件？）
│
├── check_prereqs        # 前置检查（检查什么？命令存在？目录存在？）
│   ├── for cmd in tar rsync systemctl
│   └── command -v "$cmd" || die
│
├── case $ENV in         # 环境分支（不同环境不同行为？）
│   ├── staging)    deploy staging    # ← 这个分支是你关心的
│   └── production) deploy production
│
└── deploy "$ENV"        # 核心部署逻辑
    ├── backup_current       # 先备份
    ├── rsync ... "$ENV:/opt/app/"  # 传文件
    ├── ssh "$ENV" "systemctl restart myapp"  # 远程重启
    └── wait_for_http        # 等就绪

关键问题——第二遍你要能回答：

  • 脚本的"正常路径"是什么？（假设一切顺利，走了哪些步骤？）
  • 有哪些分支？（不同环境？不同参数？）
  • 哪些步骤可能失败？失败后怎么处理？（die？rollback？）
  • 有没有外部依赖？（网络请求、SSH、数据库——这些是最容易出问题的地方）

4. 第三遍：查细节——搞懂你不认识的东西

前面两遍你可能遇到一些不认识的写法。第三遍是定点清除这些"未知符号"：

遇到什么 去哪查
不认识的命令或参数组合 type -a 命令名 确认实现，再查 man 命令名 或项目官方手册
${VAR:-default}、${VAR%.*} 速查参考：变量展开
[[ ... ]] 里面的奇怪条件 help test 或 help '[[ '（也可运行 help [[）
可疑的引用、test 或数据流 运行仓库固定版本的本地 shellcheck，再用最小失败用例验证
某个变量的值到底是多少？ bash -x script.sh——看实际展开后的值

5. 第四遍：调试验证——怀疑有 bug 怎么查

调试不是"感觉不对就加 echo"——有一套层次化的手段：

Level 1：加壳追踪——不改代码

# 最直接的调试方式——不需要改任何代码
bash -x deploy.sh staging v2.0 2>trace.log
# 输出到文件，可以慢慢看每一步变量展开后的实际命令

# 只看特定段落：在脚本里加标记
set -x          # ← 从这里开始追踪
# ... 你怀疑有问题的代码 ...
set +x          # ← 到这里结束追踪
只在隔离且允许执行副作用的环境运行 bash -x。追踪会真实执行命令，并可能把密码、令牌和个人数据写入日志。

Level 2：打印关键变量——最小侵入

# 不是漫天撒 echo，而是只在关键决策点打印
echo "[DEBUG] ENV=$ENV, VERSION=$VERSION, TARGET=${TARGET:-未设置}" >&2
#                                                         ↑
#                                   输出到 stderr，不污染 stdout 数据流

Level 3：隔离复现——把怀疑的函数拆出来

# 先确认脚本只有定义，或入口使用下面的保护条件
if [[ ${BASH_SOURCE[0]} == "$0" ]]; then
    main "$@"
fi

# 再在一次性子 Shell 中加载并调用，避免污染当前交互环境
bash -c 'source ./deploy.sh; if deploy_to_server staging; then status=0; else status=$?; fi; printf "status=%s\n" "$status"'
# 更复杂的测试应拆出函数库，并用自动化测试覆盖成功与失败分支

Level 4：ShellCheck——让机器帮你查

shellcheck deploy.sh
In deploy.sh line 15:
    rm -rf $TEMP_DIR
           ^------^ SC2086: Double quote to prevent word splitting.

# ShellCheck 能发现许多引用、test、可移植性和数据流问题；
# 静态分析无法证明业务语义、并发、安全或恢复逻辑正确。
优先运行仓库固定版本的本地 ShellCheck，不要把含凭证、内部地址或私有逻辑的脚本粘贴到公共网页。

6. 实战走读：我们一起来读一个脚本

下面是一个中等复杂度的部署脚本。用刚学的四遍法过一遍：

#!/bin/bash
# db-migrate.sh — 数据库迁移脚本
set -euo pipefail

readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
readonly MIGRATIONS_DIR="${SCRIPT_DIR}/migrations"
: "${DB_HOST:=localhost}"  : "${DB_PORT:=5432}"
: "${DB_NAME:=myapp}"      : "${DB_USER:=admin}"
: "${DB_PASSWORD:?必须设置 DB_PASSWORD}"

log() { echo "[$(date '+%H:%M:%S')] $*" >&2; }
die() { log "FATAL: $*"; exit 1; }

run_sql() {
    PGPASSWORD="$DB_PASSWORD" psql \
        -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" \
        -v ON_ERROR_STOP=1 -q "$@"
}

get_applied() {
    run_sql -t -c "SELECT filename FROM schema_migrations ORDER BY filename;" \
        2>/dev/null || echo ""
}

apply_migration() {
    local file="$1"
    log "应用迁移: $(basename "$file")"
    run_sql -f "$file" || die "迁移失败: $file"
    run_sql -c "INSERT INTO schema_migrations VALUES ('$(basename "$file")')" \
        || die "记录迁移失败: $file"
}

main() {
    local direction="${1:-up}"

    log "数据库迁移开始（方向: $direction）"
    [[ -d "$MIGRATIONS_DIR" ]] || die "迁移目录不存在: $MIGRATIONS_DIR"

    # 确保迁移记录表存在
    run_sql -c "CREATE TABLE IF NOT EXISTS schema_migrations (
        filename VARCHAR(255) PRIMARY KEY, applied_at TIMESTAMP DEFAULT now()
    );" || die "初始化迁移表失败"

    local applied
    applied=$(get_applied)

    for migration in "$MIGRATIONS_DIR"/*.sql; do
        [[ -f "$migration" ]] || continue
        local name; name=$(basename "$migration")
        if ! echo "$applied" | grep -qF "$name"; then
            apply_migration "$migration"
        fi
    done

    log "迁移完成"
}
main "$@"

第一遍：扫结构（30 秒）

  • Shebang: bash ✓
  • 失败选项: set -euo pipefail；还需检查各语法上下文和显式分支
  • 工具函数: log()、die()
  • 业务函数: run_sql()、get_applied()、apply_migration()
  • 入口: main "$@" ✓

第二遍：追主干

main "$@"
│
├─ direction = $1 (默认 "up")
├─ 创建 schema_migrations 表（不存在则建）
├─get_applied() → 查询已执行的迁移文件名列表
├─ for *.sql in migrations/
│   └─ 如果文件名不在 applied 里 → apply_migration()
│       ├─ run_sql -f 文件      # 执行 SQL
│       └─ INSERT 记录到表      # 标记为已执行
└─ "迁移完成"

第三遍：定点清除不认识的写法

  • : "${DB_PASSWORD:?必须设置}" → 参数展开（第 4 课）：未设置或为空就报错退出
  • PGPASSWORD="$DB_PASSWORD" psql ... → 临时环境变量可被同机进程观察；PostgreSQL 官方建议密码文件等更安全方式
  • run_sql -t -c "SELECT ..." → psql 的 -t 只输出数据（去表头），-c 执行单条 SQL
  • grep -qF "$name" → -F 固定字符串匹配（不把 $name 当正则）

第四遍：有什么潜在问题？

  • readonly SCRIPT_DIR="$(...)" 会让 readonly 的状态掩盖命令替换中的 cd 失败；应先单独赋值并检查，再声明只读。
  • echo "$applied" | grep -qF "$name" → 如果迁移文件名恰好是另一个文件名的前缀，-F 可能误判？这里的逻辑是"文件名完全等于某行"还是"包含"？看源码是 grep -F + 不锚定，所以只要文件名 作为子串出现就算"已执行"。如果迁移文件叫 1.sql 和 11.sql——1.sql 会匹配到 11.sql。这是一个潜在的 bug！
  • get_applied 把数据库查询失败降级为空列表，可能重新执行全部迁移；这里没有恢复语义，应该失败退出。
  • psql -t 仍可能输出对齐空白；若继续采用逐行比较，还要使用无对齐输出并准确比较整行，例如 -At 与 grep -Fxq --。
  • 执行迁移和写入记录是两次独立的 psql 调用，中途失败会留下“数据库已改、记录未写”的状态；还没有并发锁。
  • 文件名直接拼进 SQL 字符串，存在引号与 SQL 注入问题；direction 参数也没有真正控制任何行为。
  • 脚本没有定义迁移文件名规则和排序环境；数据库迁移顺序不能依赖未经约束的 glob 与 locale。
这段脚本是代码审查练习，不是迁移工具模板。真实服务优先采用成熟迁移工具，并明确事务支持、并发锁、不可事务化语句和回滚策略。
四遍法的价值是把“理解”和“验证”分开。先建骨架、再追主干、最后查细节和构造失败用例；所需时间取决于脚本副作用、外部依赖和领域规则，不能由行数直接推断。

动手练习（5 分钟）

用四遍法分析下面这段故意带缺陷的脚本。除了正常路径，重点检查：相对路径在 cd 后指向哪里、报告的生命周期、管道的子 Shell 是否真的影响结果，以及被忽略的错误是否有恢复语义。

# 这个脚本在干什么？用四遍法分析
exercise_dir=$(mktemp -d) || exit 1
mystery_script="$exercise_dir/mystery-script.sh"
cat > "$mystery_script" << 'EOF'
#!/bin/bash
set -euo pipefail

readonly BASE="${1:?用法: $0 <目录>}"
readonly OUT="${2:-report.txt}"

tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT
cd "$tmp" || exit 1

find "$BASE" -type f -name '*.log' | while IFS= read -r f; do
    bn=$(basename "$f")
    grep -c 'ERROR' "$f" > /dev/null 2>&1 || continue
    cp "$f" "${bn}.bak" 2>/dev/null || true
    sort -t' ' -k2 "$f" | awk '{print $1, $4, $5}' > "${bn}.parsed"
done

echo "=== 报告 ===" > "$OUT"
for f in *.parsed; do
    [[ -f "$f" ]] || continue
    name="${f%.parsed}"
    wc -l < "$f" >> "$OUT"
done

echo "报告已生成: $OUT"
EOF
chmod +x "$mystery_script"

# 试着回答：
# 1. 第一遍：骨架——有哪些部分？
# 2. 第二遍：主干——正常路径是什么？
# 3. 第三遍：哪些写法需要查？管道子 Shell 在这里是否真的改变结果？
# 4. 第四遍：有什么潜在问题？
# 完成后：rm -rf -- "$exercise_dir"
完成后展开复核要点
  • BASE 和 OUT 若是相对路径，会在 cd "$tmp" 后改变含义；报告还会随临时目录被删除。
  • grep -c ... || continue 把“没有匹配”和“无法读取”都当成跳过；cp ... || true 则隐藏了备份失败。
  • 不同目录中的同名日志会写入同一个 ${bn}.parsed；报告计算了 name 却没有输出它。
  • 管道确实让 while 在子 Shell 中运行，但本例没有依赖循环修改外层变量；这不是当前故障根因。

快速自检

Q1: 四遍法的"第一遍"最应该关注什么？

每一行的语法细节，确保看懂了每个符号 脚本的整体骨架——严格模式、函数分区、main入口、配置常量 寻找 bug，标记所有可疑的写法

Q2: 你在脚本里看到 ${VAR:-default} 但忘了具体含义——最好的做法是？

猜一下，根据上下文大概能推出意思 跳过它，反正不影响理解主流程 查速查参考或 Bash 手册，搞清楚再继续

Q3: 想追踪脚本每一步实际执行了什么命令，最快的做法是什么？

在每一行前面加 echo 打印行号 用 bash -x script.sh 运行 把脚本贴到 ChatGPT 让它解释

Q4: 你怀疑某个函数有 bug，想单独测试它，怎么做最合适？

复制函数代码到新文件，手动构造参数测试 确认入口有 BASH_SOURCE 保护后，在一次性子 Shell 中 source 并调用函数 在整个脚本后面加测试代码，运行脚本时会自动测试
