第 15 课 ⏱ 约 25–35 分钟

中断时终止并回收子进程

父脚本退出之前，要处理自己启动且仍归它管理的任务

第 14 课已经证明你能在正常执行路径逐项 wait 并汇总状态。本课只补一条失败路径：另一个进程只向父 Bash 发送 TERM 时，父 Bash 通过 trap 终止并回收自己记录的直接子进程，然后向调用者返回明确的中断状态。

1. 本课目标与边界

练习对象固定为一个父 Bash 和两个由它直接启动的 sleep。测试先等两个 PID 都记录完成，再向父 PID 发送 TERM。完成本课时必须同时证明：

  • 正常结束时，父脚本返回 0。
  • 只向父脚本发送 TERM 后，父脚本返回课程约定的 143。
  • 两个受管子进程都已退出，父脚本对它们执行过 wait。
本课不处理 Ctrl+C、进程组、孙进程、忽略 TERM 的程序、宽限期或 KILL 升级。那些需求会进入进程监督和进程树管理， 应由服务管理器、容器运行时或更合适的语言负责。

2. 四条因果规则

操作它完成了什么它没有完成什么
kill -TERM "$pid"向指定 PID 请求发送 TERM。不等待目标退出，也不自动通知它的子进程。
trap on_term TERM让父 Bash 收到 TERM 时执行 on_term。不自动知道应该清理哪些 PID。
wait "$pid"等待该直接子进程并取得、消费它的状态。不会主动要求仍在运行的进程终止。
exit 143执行本课明确规定的父脚本中断接口。不是 POSIX 对所有 Shell 的通用计算公式。

GNU Bash 规定：如果 Bash 正在 wait 异步任务，并收到已注册 trap 的信号，wait 会立即以大于 128 的状态返回，随后 Bash 立即执行 trap。POSIX 只要求“因信号结束”的 Shell 状态大于 128，信号与具体数值的映射 由实现决定。本课固定使用 GNU Bash 5.3.15，并主动选择 143 表示 TERM 中断。

kill 是“发出终止请求”，wait 是“确认结束并收集结果”。可靠清理需要两步，顺序也不能颠倒。

3. 固定环境中的失败基线

baseline_parent() {
  sleep 30 &
  child_pid=$!
  wait "$child_pid"
}

baseline_parent &
parent_pid=$!
kill -TERM "$parent_pid"

在课程固定的 GNU Bash 5.3.15 容器中，只向父 PID 发送 TERM，实测结果为：

parent_status=143
child_after_parent=alive

父脚本结束不会替你把刚收到的 TERM 转发给后台子进程。测试随后主动终止这个受控 sleep，因此实验没有在 容器中遗留任务。

4. 先定义清理顺序

父 Bash 收到 TERM
       │
       ▼
trap 进入 on_term
       │
       ▼
先向全部已记录 PID 发送 TERM
       │
       ▼
再逐项 wait，确认并收集状态
       │
       ▼
父 Bash exit 143

“全部发送，再全部等待”很重要：如果第一个子进程需要时间响应 TERM，其他子进程也能同时开始退出，而不是等父脚本 依次处理。

第一轮：找出会卡住的清理顺序

两个子进程都是 sleep 300。父 Bash 收到 TERM 后进入下面的 handler：

on_term() {
  local pid
  trap - TERM

  for pid in "${pids[@]}"; do
    wait "$pid"
  done

  for pid in "${pids[@]}"; do
    kill -TERM "$pid"
  done

  exit 143
}

它能否迅速完成清理？请指出进入 handler 后第一条会长期阻塞的命令，以及因此迟迟无法执行的操作。先把因果过程 发给老师，再看下一节的完整结构。

5. 完整结构

pids=()

terminate_children() {
  local pid child_status

  for pid in "${pids[@]}"; do
    if kill -TERM "$pid" 2>/dev/null; then
      printf 'child=%s action=term-sent\n' "$pid" >&2
    else
      printf 'child=%s action=term-not-sent\n' "$pid" >&2
    fi
  done

  for pid in "${pids[@]}"; do
    if wait "$pid" 2>/dev/null; then
      child_status=0
    else
      child_status=$?
    fi
    printf 'child=%s wait_status=%s\n' \
      "$pid" "$child_status" >&2
  done
}

on_term() {
  trap - TERM
  printf 'signal=TERM action=cleanup\n' >&2
  terminate_children
  exit 143
}

trap on_term TERM

sleep 300 &
pids+=("$!")
sleep 300 &
pids+=("$!")

for pid in "${pids[@]}"; do
  wait "$pid"
done

kill 失败可能表示目标已经结束；清理过程记录它，但仍继续处理其他 PID。每个 wait 都放在 if 中并立即保存非零状态，避免预期中的 TERM 状态中止清理。trap - TERM 恢复 TERM 的原始处理方式， 防止同一个 handler 递归执行；本练习不承诺抵抗连续多次 TERM。

6. 实现与验证任务

证明父脚本和子进程的最终状态

根据上面的接口实现 handler，由测试进程完成三组验证：

  1. 正常结束：两个短任务自然结束；父脚本返回 0。
  2. 运行中中断：两个长任务仍在运行时，只向父 PID 发送 TERM；父脚本返回 143，两个子 PID 均不存在。
  3. 时序变化：一个短任务已经结束、另一个仍在运行时发送 TERM；清理仍完成，父脚本返回 143。

测试必须先得到两个子 PID，再发送 TERM；检查结束后不得按命令名做宽泛 pkill。把 handler 发给老师， 由老师在一次性固定版本容器中运行验证。

7. 何时不要继续用这段 Bash

  • 外部信号可能恰好到达 command & 与 pids+=("$!") 之间，而业务要求原子地启动并登记任务。
  • 子进程会创建自己的进程树，单个 $! 不能代表全部后代。
  • 目标可能忽略 TERM，需要宽限期、KILL 升级和严格墙钟期限。
  • 要求连续信号、重启、日志、健康检查或跨平台一致的进程监督。

出现任一条件，就应交给服务管理器、容器运行时或 Python/Go 等更适合管理状态的实现。本课完成后，固定 Bash 课程结束；后续通过真实脚本和间隔复习保持能力。
