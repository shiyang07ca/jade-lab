进程管理

后台任务、信号、等待——脚本里管理多进程的正确姿势

部署脚本里经常需要：后台启动服务然后等它就绪、同时部署到多台机器、给某个命令设置超时、优雅地杀掉旧进程再启新的。这些操作的本质都是进程管理——理解 &、wait、kill 和信号，你就能看懂并编写这些关键逻辑。

1. &：把命令放到后台

这是最简单也最常见的进程操作——在命令末尾加 &，Shell 不等待它完成，立即返回提示符：

sleep 10 &               # 后台睡 10 秒，Shell 立刻返回
[1] 12345               # [作业号] PID

echo "我不用等 sleep"    # 立即执行
我不用等 sleep

部署脚本里最典型的用法——启动服务然后继续做别的事：

# 启动服务后立即开始健康检查
./myapp &
APP_PID=$!                      # $! = 最后一个后台进程的 PID
echo "应用已启动，PID: $APP_PID"

# 有期限地轮询；同时确认子进程没有提前退出
deadline=$((SECONDS + 30))
until curl -fsS --connect-timeout 1 --max-time 2 http://localhost:8080/health >/dev/null; do
    kill -0 "$APP_PID" 2>/dev/null || { wait "$APP_PID"; exit $?; }
    (( SECONDS < deadline )) || { kill "$APP_PID"; exit 1; }
    sleep 0.5
done
echo "服务就绪！"

2. $!、$$、wait：跟踪和控制后台进程

变量/命令 含义 典型用法
$! 最后一个后台进程的 PID myapp & PID=$!
$$ 当前 Shell/脚本自身的 PID printf 'pid=%s\n' "$$"（日志关联）
wait PID 等待指定进程结束 wait "$PID"; echo "进程结束，退出码: $?"
wait（无参数） 等待所有后台子进程结束 wait; echo "全部完成"

wait 是部署脚本里做并行操作的核心：

# 同时部署到三台服务器；函数本身保持前台语义
deploy_to() { rsync -avz ./build/ "$1:/opt/myapp/"; }

deploy_to server1 &    PID1=$!
deploy_to server2 &    PID2=$!
deploy_to server3 &    PID3=$!

info "并行部署中... PID: $PID1 $PID2 $PID3"

# 分别 wait，不能只看最后一个 PID 的状态
failed=0
for pid in "$PID1" "$PID2" "$PID3"; do
    if ! wait "$pid"; then
        error "部署子进程失败: $pid"
        failed=1
    fi
done
(( failed == 0 )) || die "至少一台服务器部署失败"
info "三台服务器全部部署完成"
并行部署最大的好处是耗时由最慢的那台决定而非三者之和。三台各需 5 分钟，串行 15 分钟，并行 5 分钟。但要注意——`wait` 返回最后一个参数的退出码，要检查每个进程的成败还需要各自捕获。

3. 子 Shell：( ) 分组命令

(cmd1; cmd2) 在一个子 Shell 中执行——里面的 `cd`、变量赋值不会影响外层：

pwd && (cd /tmp && pwd) && pwd
/home/alice
/tmp
/home/alice               # ← 回到原目录！子 Shell 的 cd 不影响外层

X=1; (X=2; echo "子Shell: X=$X"); echo "外层: X=$X"
子Shell: X=2
外层: X=1

对比：{ cmd1; cmd2; } 在当前 Shell 执行（大括号内最后一个命令后必须加分号或换行，且括号两边必须有空格）：

X=1; { X=2; echo "大括号: X=$X"; }; echo "外层: X=$X"
大括号: X=2
外层: X=2                # ← X 被改了！大括号不创建子 Shell
在 Bash 默认设置下，管道的各段在子 Shell 中运行，所以 X=1; echo "hello" | while read line; do X=2; done; echo $X 输出 1。lastpipe 在非交互且关闭作业控制等条件下可以让最后一段在当前 Shell 执行，因此不要依赖隐含状态。需要保留循环修改时可用进程替换：while read -r line; do ...; done < <(printf '%s\n' hello)。

4. 信号：和进程对话的基本方式

信号是操作系统发给进程的简短消息。最常打交道的几个：

信号 常见编号 触发方式 含义
SIGINT2Ctrl+C中断——"请停下来"
SIGTERM15kill PID（默认）终止——"请优雅退出"（进程可以清理后退出）
SIGKILL9kill -9 PID强制杀死——操作系统直接干掉进程，无法被捕获
SIGHUP1终端关闭挂断——"你的终端没了"（常用于让守护进程重载配置）
SIGUSR1/USR2因平台而异kill -USR1 PID用户自定义——含义由应用定义 
kill 12345             # 发 SIGTERM → "请你自己退出"
kill -9 12345          # 发 SIGKILL → "立刻死，不留遗言"
kill -HUP 12345        # 发 SIGHUP → 很多守护进程用这个作为"重载配置"的信号
pgrep -af "myapp"      # 先检查匹配范围；pkill -f 可能误伤相似命令行
kill -0 12345          # 不发实际信号；0 表示存在且当前用户有权限发送信号
通常先发送 SIGTERM，并在有明确期限的循环中等待；超时后是否发送 SIGKILL 取决于服务恢复策略。优先按信号名写 kill -TERM，不要把平台相关编号写入可移植脚本。只对已经验证身份的 PID 操作，防止 PID 复用后误伤其他进程。

5. trap 处理信号：优雅退出的关键

第 8 课学了 `trap ... EXIT`。对于信号处理，trap 同样适用——让你的脚本在被 Ctrl+C 或 kill 时有机会清理：

# 部署脚本里经典的多信号处理
cleanup() {
    local exit_code=$?
    trap - EXIT
    info "收到退出信号，正在清理..."

    # 这里只处理由当前脚本启动并记录的子进程
    if [[ -n "${APP_PID:-}" ]] && kill -0 "$APP_PID" 2>/dev/null; then
        kill -TERM "$APP_PID"
        local attempt
        for attempt in {1..50}; do
            kill -0 "$APP_PID" 2>/dev/null || break
            sleep 0.1
        done
        kill -0 "$APP_PID" 2>/dev/null && kill -KILL "$APP_PID"
        wait "$APP_PID" 2>/dev/null || true
    fi

    exec 200>&- 2>/dev/null || true
    info "清理完成（退出码: $exit_code）"
    return "$exit_code"
}
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM

6. nohup 和 disown：让进程在终端关闭后继续活着

终端挂断、交互式 Shell 的作业控制选项和进程的会话关系都会影响 SIGHUP。nohup 与 disown 能改变其中一部分行为，但不等于服务管理：

# 方式 1：nohup —— 启动时就"免疫" SIGHUP
nohup ./long-task.sh > task.log 2>&1 &
#  本例已显式写 task.log；未重定向且连接终端时 nohup 才选择 nohup.out

# 方式 2：disown —— 从当前 Bash 的作业表移除作业
./long-task.sh &
disown %1        # 或 disown 12345（用 PID）
#   Bash 不再把它当受管理作业；这不会改变父 PID 或修复终端 I/O
nohup 让目标忽略 SIGHUP，并在标准流连接终端时调整重定向；它不提供自动重启、日志轮转、依赖管理或健康检查。长期进程应交给 systemd、容器运行时等服务管理器。

7. 实战模式

模式 A：给命令设置超时

# GNU coreutils timeout：5 秒发 TERM，再给 2 秒清理时间
if timeout --signal=TERM --kill-after=2s 5s \
    curl -fsS --connect-timeout 2 https://slow-api.example.com; then
    info "请求成功"
else
    status=$?
    if [[ $status -eq 124 ]]; then
        error "请求超时"
    else
        error "请求失败（状态: $status）"
    fi
fi
GNU timeout 不是 POSIX 接口，macOS 默认也不提供同一命令。优先使用程序自身的期限选项（例如 curl 的 --connect-timeout 和 --max-time）；自制“sleep 后 kill PID”容易遇到 PID 复用、子进程树和竞态。

模式 B：长期进程交给服务管理器

# Linux/systemd 示例：进程身份、重启和日志由服务管理器负责
systemctl start myapp
systemctl is-active --quiet myapp || die "myapp 未进入 active 状态"
systemctl stop myapp

纯 PID 文件只保存一个可复用的整数，不能证明当前 PID 仍是原进程；kill -0 也会受权限影响。若必须兼容旧式 PID 文件，至少要验证文件所有者、整数格式、进程启动时间和可执行文件身份，并对读取后到发信号之间的竞态有明确处理。

动手练习（5 分钟）

# 1. 体验后台进程 + $! + wait
sleep 3 & PID=$!; echo "后台 PID: $PID"; wait $PID; echo "退出码: $?"

# 2. 并行执行三个任务
for i in 1 2 3; do (sleep $i && echo "任务$i 完成") & done; wait; echo "全部完成"

# 3. 体验子 Shell 的隔离效果
X=100; (X=200; echo "子Shell内: $X"); echo "子Shell外: $X"

# 4. trap 捕获 Ctrl+C
trap 'echo "  → 捕获到中断信号"; trap - INT' INT; echo "按 Ctrl+C 试试..."; sleep 30

# 5. kill -0 检查进程是否存在
sleep 60 & SPID=$!; kill -0 $SPID && echo "进程 $SPID 存活"; kill $SPID

快速自检

Q1: myapp & 后再对该作业执行 disown，改变的是什么？

前者是后台进程，后者是前台进程 该作业从 Bash 作业表移除；这不等于完整的服务存活保证 前者启动更快，后者需要额外的进程 fork

Q2: `kill -9` 和 `kill`（默认 SIGTERM）的关键区别是？

SIGTERM 可以被进程捕获并清理后退出；SIGKILL 直接强制杀死，进程来不及清理 SIGTERM 是 POSIX 标准，SIGKILL 是 Linux 独有的扩展 SIGTERM 杀死进程更快，SIGKILL 需要等待 I/O 完成

Q3: `X=1; (X=2); echo $X` 输出 1 还是 2？

输出 1——子 Shell 中对 X 的修改不影响外层 输出 2——子 Shell 中的变量赋值会泄漏到外层 报错——子 Shell 中不能修改变量

Q4: 部署脚本里 `wait`（无参数）的典型用途是？

暂停脚本直到用户按回车 等待所有之前用 & 启动的后台任务全部完成 等待上一条命令完成，等价于没有 & 的效果
