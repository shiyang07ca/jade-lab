第 14 课 ⏱ 约 25–35 分钟

汇总后台任务状态

启动多个任务不难，难的是让父 Shell 对每个结果负责

第 10 课介绍过 &、$! 和 wait，但历史记录只证明当时能识别概念。本课不增加新的 并发框架，而是完成一个真实自动化必须具备的能力：三个后台任务中任意一个失败，父脚本都能指出失败对象、保留其 状态，并给调用者一个明确的整体结果。

1. 本课只学什么

本课聚焦一条完整因果链：

command &
   │ 立即返回状态 0
   ▼
$! 保存刚启动任务的 PID
   │
   ▼
wait "$pid" 取得该任务的真实状态
   │
   ▼
父 Shell 按公开规则汇总所有任务

完成后，你应该能：

  • 解释为什么 command & 的即时成功不代表后台任务最终成功。
  • 在启动下一个任务前保存 $!，并保持 PID 与任务名称的对应关系。
  • 逐个执行 wait "$pid"，取得每个任务自己的退出状态。
  • 实现“全部任务都执行；任一失败则整体失败”的 collect-all 策略。
本课不处理 Ctrl+C、SIGTERM 或取消仍在运行的任务。那需要另外定义中断状态、子进程所有权和清理顺序，属于第 15 课。

2. 四条必须准确掌握的规则

写法Bash 行为本课用途
command &异步启动；父 Shell 不等待，当前异步命令的状态为 0。只说明任务已被放到后台。
$!最近放入后台的作业 PID。必须在下一次后台启动前立即保存。
wait "$pid"等待指定子进程并返回它的退出状态。把异步任务的最终结果带回父 Shell。
wait无参数时等待所有后台任务，但返回状态为 0。只能等完，不能汇总每项成败。
“等待所有任务结束”和“知道所有任务是否成功”是两个不同需求。无参数 wait 只满足前者；要满足后者，父 Shell 必须保存 PID 并逐项等待。

3. 先定义批处理接口

没有“并行脚本天然应该如何失败”的通用答案。本练习先固定以下接口：

  • 三个任务启动后都允许执行完；一个任务失败不会取消其他任务。
  • 成功任务写一行摘要到 stdout。
  • 失败任务把名称和原始退出状态写到 stderr。
  • 全部成功时脚本返回 0；只要有一项失败，脚本最终返回 1。

最终状态使用 1 表示“批次含失败”，而不是假装一个状态码能携带多个子任务状态；每项原始状态保留在诊断中。

4. 有缺陷的版本

run_job() {
    local name=$1 delay=$2 status=$3
    sleep "$delay"
    printf 'job=%s finished\n' "$name"
    return "$status"
}

run_job alpha 1 0 &
run_job beta  2 7 &
run_job gamma 3 0 &

wait
printf 'batch complete\n'

这里的 beta 最终返回 7，但父脚本没有保存任何 PID。无参数 wait 会等三个任务全部结束，却返回 0； 最后的 printf 也返回 0。调用方因此看见“批次成功”。

第一轮：只追状态，不改代码

  1. 三条 run_job ... & 在父 Shell 中各自立即产生什么状态。
  2. beta 的真实状态存在于哪里，父 Shell 通过什么操作才能取得。
  3. 无参数 wait 返回什么；最后整个脚本返回什么。

5. 正确结构：先看一个任务，再扩展到三个

先不用数组。对于一个任务，任务名写在代码里，PID 保存到一个变量：

run_job beta 2 7 &
beta_pid=$!

if wait "$beta_pid"; then
    printf 'job=beta status=0\n'
else
    beta_status=$?
    printf 'job=beta status=%s\n' "$beta_status" >&2
fi

有三个任务时，可以分别写 alpha_pid、beta_pid 和 gamma_pid。但等待和报告逻辑会重复 三遍。索引数组只是把这三组同样的数据放在连续位置。假设一次运行得到以下 PID：

names=(alpha beta gamma)
pids=(43101 43102 43103)
索引 i"${names[$i]}""${pids[$i]}"
0alpha43101
1beta43102
2gamma43103

"${!pids[@]}" 展开的是 pids 的全部索引，也就是 0 1 2。循环每次用同一个 索引 i 同时取任务名和 PID，因此二者不会错配：

for i in "${!pids[@]}"; do
    printf 'index=%s name=%s pid=%s\n' \
        "$i" "${names[$i]}" "${pids[$i]}"
done

真实 PID 每次运行都会变化，所以启动任务时动态追加任务名和刚得到的 PID：

names=()
pids=()

start_job() {
    local name=$1 delay=$2 status=$3
    run_job "$name" "$delay" "$status" &
    names+=("$name")
    pids+=("$!")
}

$! 必须紧跟后台启动保存；任何新的后台命令都会改变它。接着由父 Shell 按照索引逐项等待：

collect_results() {
    local batch_status=0 child_status i

    for i in "${!pids[@]}"; do
        if wait "${pids[$i]}"; then
            printf 'job=%s status=0\n' "${names[$i]}"
        else
            child_status=$?
            printf 'job=%s status=%s\n' \
                "${names[$i]}" "$child_status" >&2
            batch_status=1
        fi
    done

    return "$batch_status"
}

wait 放在 if 条件中，因此可以显式处理非零状态，不依赖 set -e。失败分支第一条命令 立即保存 $?；这里不能写成 if ! wait ...，否则取反会丢掉子任务原始状态。

6. 学习任务

实现并证明 collect-all 策略

把上面的函数组合成一个约 35–50 行的临时脚本，并完成三组验证：

  1. 全部成功：三个任务状态都是 0；stdout 有三项结果，stderr 为空，脚本状态为 0。
  2. 单项失败：beta 返回 7；三个任务都完成，stderr 保留 beta 与 7，脚本状态为 1。
  3. 完成顺序变化：调整 delay，使任务按不同顺序结束；名称仍必须对应正确状态。

验证重点不是运行速度，而是 PID、名称和退出状态没有因完成顺序变化而错配。

7. 本课边界与第 15 课

本课选择 collect-all：即使某项失败，也等待其他项完成。真实自动化还可能需要 fail-fast，但取消任务会立刻引入 新的问题：父脚本收到信号时谁负责通知子进程、已经结束的 PID 如何移出清理集合、以及退出前为什么仍要 wait。

第 15 课只处理这条中断路径：向父脚本发送 SIGTERM，父脚本显式终止自己启动且仍在运行的子进程，逐个回收， 并向调用者返回明确的中断状态。完成后，固定课程结束，后续只在真实任务中按需学习。
