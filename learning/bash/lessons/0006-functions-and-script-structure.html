函数与脚本结构

把代码打包成可复用的积木，写出有清晰结构的脚本

部署脚本不应该是一堆命令从上堆到下。你会看到 deploy_app() { ... }、rollback() { ... }、check_prereqs() { ... } 这样的函数，以及 main "$@" 的入口模式。这一课就是让你看懂这些结构的含义，并学会自己写。

1. 函数的本质：给一组命令起个名字

函数就是一段你给起了名字的代码，以后叫这个名字就执行它。Bash 里定义函数有两种写法：

# 写法 1：函数名 + 小括号 + 大括号（推荐；POSIX sh 也支持）
say_hello() {
    echo "Hello, $1!"
}

# 写法 2：function 关键字（Bash 专属，同样可用）
function say_hello {
    echo "Hello, $1!"
}

# 二选一即可，本书使用写法 1

调用函数——直接写名字就行，不像 Python 要加括号：

say_hello "World"      # → Hello, World!
say_hello "Bash"       # → Hello, Bash!

2. 函数的参数：用位置参数 $1、$2 接收

这是最容易困惑的地方：函数内部有一套独立的位置参数。脚本的 $1 和函数内的 $1 是两回事——函数调用时，传入的参数会"覆盖"掉脚本级的 $1、$2……

cat > /tmp/func-args.sh << 'EOF'
#!/bin/bash

deploy() {
    echo "    函数 deploy 的第 1 个参数: $1"
    echo "    函数 deploy 的第 2 个参数: $2"
    echo "    函数 deploy 的所有参数: $@"
}

echo "脚本级的 \$1: $1"        # ← 脚本的第一个参数
deploy staging v2.0          # ← 调用函数，传入两个参数
echo "脚本级的 \$1 仍然是: $1"  # ← 函数调用完毕后，$1 恢复原值
EOF
bash /tmp/func-args.sh production
脚本级的 $1: production
    函数 deploy 的第 1 个参数: staging
    函数 deploy 的第 2 个参数: v2.0
    函数 deploy 的所有参数: staging v2.0
脚本级的 $1 仍然是: production
记忆模型：调用函数就像调用一个"迷你脚本"。函数内部 $1 是调用者传入的第一个参数，$@ 是所有参数——和第 4 课学的特殊变量规则完全一致。函数一结束，脚本级的位置参数恢复原值。脚本入口处习惯用 main "$@" 把脚本参数原样传进主函数。

3. local：防止变量"泄漏"

Bash 函数里定义的变量默认是全局的——函数一运行，外面的同名变量就被改了：

VERSION="v1"

update_version() {
    VERSION="v2"            # ⚠️ 没加 local，修改了外部的 VERSION！
}
update_version
echo "$VERSION"             # → v2 —— 外面的变量被改了！

# 正确做法：用 local 声明局部变量
safe_update() {
    local VERSION="v3"      # ✅ local 限定变量只在函数内有效
    echo "函数内: $VERSION"
}
safe_update                 # → 函数内: v3
echo "$VERSION"             # → v2 —— 外面的变量不受影响
在 Bash 函数中，临时变量默认使用 local，除非函数有意修改外部状态。local 是 Bash 等 Shell 的扩展，不属于 POSIX sh。此外，local VAR=$(cmd) 可能掩盖命令替换的退出码；需要检查失败时分开写：local VAR; VAR=$(cmd)。

4. 函数的"返回值"：两个机制，别搞混

Bash 函数不能像 Python 那样 return 一个字符串。它有两种不同的"返回"方式：

# 机制 1：return N —— 返回退出码（0-255）
is_port_open() {
    nc -z localhost "$1" > /dev/null 2>&1
    return $?               # 返回 nc 的退出码（0=开放，1=关闭）
    # 实际上不需要手动 return $?——函数默认返回最后一条命令的退出码
}

# 机制 2：echo + 命令替换 —— "返回"字符串数据
get_timestamp() {
    local ts
    ts=$(date +%Y%m%d_%H%M%S)
    echo "$ts"              # stdout 输出 = 函数的"返回值"
}

# 使用这两种函数
if is_port_open 8080; then          # ← 判断退出码（类似 if grep ...）
    echo "端口已开放"
fi

BACKUP_FILE="backup_$(get_timestamp).tar.gz"  # ← 捕获 stdout
echo "备份文件: $BACKUP_FILE"
一条原则分清楚：需要判断成功/失败 → 用退出码（函数内部最后一条命令的退出码自然流出，或手动 return N）。需要拿到一段数据 → 用 stdout（函数内部 echo 输出，外部 $(func) 捕获）。注意：函数内部所有 echo 都会被调用者捕获，所以调试信息要用 echo "debug" >&2 输出到 stderr 避免干扰。

5. 脚本结构：一个成熟的部署脚本长什么样？

有经验的工程师写的脚本通常遵循一个清晰的结构模式：

#!/bin/bash
# ============================================================
# deploy.sh — 应用部署脚本
# 用法: ./deploy.sh [staging|production] [版本号]
# ============================================================

# ---- 1. 严格模式 ----
set -euo pipefail

# ---- 2. 全局配置 ----
readonly APP_NAME="myapp"
readonly APP_HOME="/opt/${APP_NAME}"
readonly BACKUP_DIR="${APP_HOME}/backups"

# ---- 3. 工具函数 ----
die() {
    echo "[FATAL] $*" >&2
    exit 1
}

log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*"
}

# ---- 4. 业务函数 ----
check_prereqs() {
    local missing=()
    for cmd in rsync tar systemctl; do
        command -v "$cmd" > /dev/null || missing+=("$cmd")
    done
    if [[ ${#missing[@]} -gt 0 ]]; then
        die "缺少必要命令: ${missing[*]}"
    fi
    log "前置检查通过"
}

do_backup() {
    local timestamp="$1"
    local backup_path="${BACKUP_DIR}/${APP_NAME}_${timestamp}.tar.gz"
    log "创建备份: $backup_path"
    tar -czf "$backup_path" -C "$APP_HOME" . || die "备份失败"
    echo "$backup_path"   # ← "返回"备份路径
}

deploy_new_version() {
    local env="$1"
    local version="$2"
    local timestamp
    timestamp=$(date +%Y%m%d_%H%M%S)

    log "开始部署 $version 到 $env 环境"
    local backup_file
    backup_file=$(do_backup "$timestamp")  # ← 捕获函数 stdout 作为"返回值"

    if rsync -avz "./releases/$version/" "$APP_HOME/"; then
        log "部署成功，备份位于: $backup_file"
    else
        die "部署失败，请从备份恢复: $backup_file"
    fi
}

# ---- 5. 主入口 ----
main() {
    local env="${1:-}"
    local version="${2:-latest}"

    [[ -z "$env" ]] && die "用法: $0 <staging|production> [版本号]"
    [[ "$env" != "staging" && "$env" != "production" ]] && die "无效环境: $env"

    check_prereqs
    deploy_new_version "$env" "$version"
    log "全部完成！"
}

# ---- 6. 执行入口 ----
main "$@"

这是适合中等规模 Bash 脚本的一种可维护结构，不是唯一模板。短小脚本可以减少层次；状态多、并发复杂或需要强类型时，应改用更适合的语言：

#!/usr/bin/env bash      ← ① Shebang：通过当前 PATH 选择 Bash
set -euo pipefail        ← ② 组合错误策略（有重要例外，第 8 课详解）
readonly CONFIG="..."    ← ③ 全局常量：配置集中管理
log() / die() { ... }   ← ④ 工具函数：日志、错误处理
deploy() / backup() {}  ← ⑤ 业务函数：具体的部署逻辑
main "$@"               ← ⑥ 主入口：把脚本参数传入 main

6. 脚本的两种运行方式：执行 vs 引入

# 方式 1：作为独立脚本执行——启动一个新 Shell
./deploy.sh staging v2.0
bash deploy.sh staging v2.0

# 方式 2：引入（source）——在当前 Shell 中执行
source lib/utils.sh        # source 的简写：. lib/utils.sh

# 区别：执行是新进程，引入是当前进程
# ./script.sh 里定义的变量和函数在脚本结束后消失
# . script.sh 里定义的变量和函数会留在当前 Shell 中
./script.sh（执行） . script.sh（引入）
新进程？ 是（fork + exec） 否（当前 Shell 直接执行）
变量/函数保留？ ❌ 脚本结束就消失 ✅ 留在当前 Shell
需要执行权限？ 需要 chmod +x 不需要
典型用途 部署脚本、独立程序 加载函数库、设置环境变量（如 .bashrc）
部署脚本里的一个常见模式：如果你看到 SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)" 然后 source "${SCRIPT_DIR}/lib/utils.sh"——这是脚本在引入同一目录下的函数库。${BASH_SOURCE[0]} 比 $0 更可靠（source 进来的脚本里，$0 是调用者的名字，不是自己的名字）。

7. 实战模式：几个你马上用得上的函数

# 模式 1：等待一个服务就绪（超时保护）
wait_for_service() {
    local host="$1"
    local port="$2"
    local timeout="${3:-30}"
    local elapsed=0
    while [[ $elapsed -lt $timeout ]]; do
        if nc -z "$host" "$port" > /dev/null 2>&1; then
            log "$host:$port 已就绪"
            return 0
        fi
        sleep 1
        ((elapsed++))
    done
    die "$host:$port 在 ${timeout}s 内未就绪"
}

# 模式 2：安全地在临时目录中工作（退出后自动清理）
work_in_temp() (
    local temp_dir
    temp_dir=$(mktemp -d) || die "无法创建临时目录"
    trap 'rm -rf -- "$temp_dir"' EXIT # trap 和局部变量只属于该子 Shell
    cd "$temp_dir" || die "无法进入临时目录"
    log "工作于临时目录: $temp_dir"
)

# 模式 3：确认危险操作
confirm() {
    local prompt="${1:-确定继续？(yes/no) }"
    local answer
    read -r -p "$prompt" answer
    [[ "$answer" = "yes" ]]
}

#!/bin/bash
set -euo pipefail

die() { echo "[FATAL] $*" >&2; exit 1; }

count_lines() { wc -l < "$1"; }

main() {
    local target="${1:-}"
    [[ -z "$target" ]] && die "用法: $0 <文件路径>"
    [[ ! -f "$target" ]] && die "文件不存在: $target"
    local count
    count=$(count_lines "$target")
    echo "文件 $target 有 $count 行"
}
main "$@"
EOF

快速自检

Q1: 函数 sum() { echo $(( $1 + $2 )); }，调用者怎么写才能拿到结果 8？

result=sum(3, 5) result=$(sum 3 5) result=sum 3 5

Q2: 下面这段代码有什么问题？

set_version() {
    VERSION="$1"
}
VERSION="v1"
set_version "v2"
echo "$VERSION"  # 期望：v1，实际：v2
函数内部应该用 local VERSION="$1" 限制作用域 函数名不能有下划线 函数参数不能直接赋给变量

Q3: . lib/utils.sh 和 ./lib/utils.sh 的关键区别是？

前者在当前 Shell 执行，函数和变量保留；后者启动新进程，结束后不保留 前者需要执行权限，后者不需要 两者完全一样，只是写法不同

Q4: 部署脚本末尾 main "$@" 中，"$@" 的作用是什么？

把脚本的命令行参数原样传递进 main 函数 告诉 main 函数要接收多少个参数 把 main 函数的返回值打印出来
