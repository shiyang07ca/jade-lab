错误处理与调试

先定义失败语义，再选择 Shell 选项、显式分支、清理和诊断手段

可靠脚本必须先定义失败语义：哪些非零状态是预期分支，哪些必须停止，退出前需要清理什么，以及如何定位根因。set -euo pipefail 可以辅助发现部分错误，但不能代替显式检查和测试。

1. 痛点：默认情况下，Bash 不会因为你出错而停下来

先看一个反面教材——这段代码有一个 bug，但 Bash 会若无其事地跑完：

#!/bin/bash
# 反例：没有检查 cd 的结果

cd /nonexistent           # 这行失败了！cd 报错
echo "当前目录: $(pwd)"   # 但脚本继续执行——你还在原来的目录
printf '将会操作错误目录: %s\n' "$PWD"  # 实际仍在原目录；真实清理命令会造成破坏
echo "清理完成"
Bash 默认不会因为简单命令返回非零就自动终止脚本，而且命令是否打印诊断信息由命令自己决定。自动化脚本应显式处理关键步骤的状态；常用的 set -euo pipefail 只是社区俗称的“严格模式”，它有上下文相关的例外。

2. set -e：在规定上下文遇到非零状态时退出

-e（errexit）会让 Shell 在特定上下文中的命令返回非零时退出。先看一个不处于例外上下文的简单情况：

script=$(mktemp)
cat > "$script" << 'EOF'
#!/bin/bash
set -e
echo "第一步：正常执行"
cd /nonexistent          # 失败！退出码 ≠ 0 → 脚本在这里终止
echo "第二步：永远不会执行到这里"
EOF
bash "$script"
第一步：正常执行
<temp-script>: line 4: cd: /nonexistent: No such file or directory
rm -f -- "$script"

但 set -e 有几个"安全阀"——以下场景命令失败不会触发退出：

# 1. if / while / until 的条件部分——它们本来就在"测试"命令
if grep "ERROR" app.log; then   # grep 没找到（退出码 1），不会触发 set -e
    echo "有错误"
fi

# 2. 管道中除最后一项之外的命令（除非启用 pipefail）
false | true                     # false 失败，但管道整体以 true 的退出码为准

# 3. && / || 列表中除最后一项外的命令，以及 ! 反转的命令
false && echo "不会执行"         # false 用来决定是否执行右侧
! false                           # ! 把状态反转为 0
set -e 不是“捕获异常”。除了上述规则，函数或子 Shell 作为条件执行、命令替换和不同 Bash 兼容模式还会影响行为。关键操作仍应写成 if command; then ... else ... fi 或 command || die ...，让预期状态可读、可测试。

3. set -u：用了未定义的变量？报错退出

-u = unset。在本课的非交互式脚本中，展开未设置变量会打印诊断并使 Shell 退出； 位置参数、数组和交互式 Shell 还有手册规定的细节：

script=$(mktemp)
cat > "$script" << 'EOF'
#!/bin/bash
set -u
echo "部署到: $DEPLOY_TARGET"
EOF
bash "$script"
<temp-script>: line 3: DEPLOY_TARGET: unbound variable
rm -f -- "$script"

这能防止因变量名打错（`$CONFG` 而不是 `$CONFIG`）导致的静默错误。如果你确实需要"变量可能未设置"的行为，用参数展开提供默认值：

echo "部署到: ${DEPLOY_TARGET:-production}"   # 未设置时用 "production"

4. set -o pipefail：管道中任何命令失败都算失败

默认情况下，管道的退出码是最后一个命令的退出码：

cat missing.log | wc -l
#   ↑ 失败了         ↑ 仍成功输出 0
# 管道状态 = wc -l 的状态 = 0——cat 的失败没有体现在管道状态中
echo $?
0

开启 pipefail 后，管道返回最右侧非零命令的状态；全部成功时返回 0：

set -o pipefail
cat missing.log | wc -l
cat: missing.log: No such file or directory
       0
echo $?
1    # ← 本例只有 cat 返回非零，因此状态来自 cat

5. 常见错误处理选项组合

许多以 Bash 为明确运行时的自动化脚本使用这个组合，但是否启用应由脚本的失败语义决定：

#!/bin/bash
set -euo pipefail
# -e: 在 Bash 规定的上下文遇到非零状态时退出
# -u: 未定义变量 → 退出
# -o pipefail: 管道返回最右侧非零状态

IFS 控制部分分词和 read 的字段拆分，不是这组选项的一部分。不要全局修改；只在读取特定格式时局部指定，例如 while IFS=: read -r user _ uid _; do ...; done。

set -e 的规则来自 Shell 语法上下文：函数调用位于条件中时，函数体可能不受 errexit 影响；let 或 (( )) 的算术结果为 0 时状态也是非零。不要用覆盖率百分比描述它，应针对脚本真实分支编写测试，并以 GNU Bash 手册的 The Set Builtin 为准。

6. trap：注册退出时的清理逻辑

trap 为指定信号或 Shell 的 EXIT 事件注册命令。它可以集中清理，但不是异常系统中的完整 finally：哪些路径触发、处理器如何继承以及原状态是否保留，都要按 Bash 规则验证。

最常用的三种 trap

# trap '命令' 信号

# EXIT  —— Shell 按普通退出流程终止时
trap 'rm -rf -- "$TEMP_DIR"' EXIT

# ERR   —— 遵循与 errexit 相近的语法例外；set -E 扩展其继承范围
trap 'echo "脚本在第 $LINENO 行失败" >&2' ERR

# INT/TERM —— 用户按 Ctrl+C (SIGINT) 或被 kill (SIGTERM) 时
trap 'echo "收到 SIGINT" >&2; exit 130' INT
trap 'echo "收到 SIGTERM" >&2; exit 143' TERM

部署脚本里的 trap 模式

#!/bin/bash
set -Eeuo pipefail

TEMP_DIR=$(mktemp -d)

# 无论如何退出都要清理
cleanup() {
    local exit_code=$?
    trap - EXIT
    printf '清理中...\n' >&2
    rm -rf -- "$TEMP_DIR" || printf '清理失败: %s\n' "$TEMP_DIR" >&2
    printf '退出状态: %s\n' "$exit_code" >&2
    exit "$exit_code"
}
trap cleanup EXIT

# 出错时额外记录
on_error() {
    echo "[ERROR] 脚本在第 ${1:-?} 行失败" >&2
}
trap 'on_error $LINENO' ERR

# --- 主逻辑 ---
echo "部署开始，工作目录: $TEMP_DIR"
# ... 部署步骤 ...
# 脚本结束时，cleanup 自动执行——你不需要记得在每一处 exit 前写清理代码
EXIT trap 适合集中清理当前 Shell 创建的临时资源。 它覆盖正常结束、显式 exit 和常见错误退出；但 SIGKILL、主机崩溃或 exec 成功替换当前 Shell 等路径不会执行它。清理操作应保持幂等，并且不能把临时文件清理误写成业务回滚。

7. set -x：查看展开后执行的命令

当你面对一个脚本不理解它的行为时，set -x 是最直接有效的调试工具：

script=$(mktemp)
cat > "$script" << 'EOF'
#!/bin/bash
set -Eeuo pipefail

NAME="alice"
GREETING="Hello, ${NAME}"
DIR="${HOME}/projects"

cd "$DIR" || exit 1
echo "$GREETING"
ls -la
EOF

bash -x "$script"
+ NAME=alice
+ GREETING='Hello, alice'
+ DIR=/home/alice/projects
+ cd /home/alice/projects
+ echo 'Hello, alice'
Hello, alice
+ ls -la
...（文件列表）
rm -f -- "$script"

每一行前面有 + 号的都是 Bash 实际执行的命令（变量已展开），你可以逐行追踪脚本到底执行了什么。也可以只在脚本的某一段开启：

set -x 会打印展开后的参数，可能泄露令牌、密码或个人数据。处理敏感值前先 set +x，并按敏感数据管理调试日志。
set -x              # 开始追踪
# ... 你怀疑有 bug 的那几行 ...
set +x              # 关闭追踪

更精细的调试——把追踪输出重定向到文件：

bash -x deploy.sh 2>debug.log   # -x 输出到 stderr，重定向到文件慢慢看

8. die() 模式：把错误处理和日志合并

现在你理解了所有零件，看部署脚本里最常见的错误处理模式——它对第 6 课的函数结构做了专门化：

#!/bin/bash
set -euo pipefail

readonly SCRIPT_NAME="${0##*/}"

# 致命错误：打印消息并退出
die() {
    echo "[${SCRIPT_NAME}] FATAL: $*" >&2
    exit 1
}

# 仅警告
warn() {
    echo "[${SCRIPT_NAME}] WARN: $*" >&2
}

# 信息日志
info() {
    echo "[${SCRIPT_NAME}] $(date '+%H:%M:%S') $*"
}

# 使用
[[ -d "$DEPLOY_DIR" ]] || die "部署目录不存在: $DEPLOY_DIR"
[[ -f "$CONFIG_FILE" ]] || die "配置文件不存在: $CONFIG_FILE"

command -v docker > /dev/null || die "需要 Docker 但未安装"

info "开始部署..."
# ... 部署逻辑 ...
info "部署完成"
一个实用起点是：① 根据明确的失败语义选择 Shell 选项；② 用 EXIT trap 清理当前进程创建的临时资源；③ 对边界输入和关键命令显式检查并保留错误上下文。最后仍需用失败场景测试验证行为。

9. 常见错误处理模式速查

# 模式 1：不能失败的关键命令就用 || die
tar -czf "$BACKUP" "$DIR" || die "备份失败"

# 模式 2：预期“未匹配”时显式分支，不吞掉读取错误等其他状态
if grep -q "optional-pattern" config.ini; then
    info "找到可选配置"
elif [[ $? -ne 1 ]]; then
    die "读取配置失败"
fi

# 模式 3：失败后重试
check_health() {
    local i
    for i in {1..3}; do
        if curl -fsS --connect-timeout 2 --max-time 5 https://api.example.com/health; then
            return 0
        fi
        if [[ $i -lt 3 ]]; then
            warn "第 $i/3 次探测失败，2 秒后再次尝试"
            sleep 2 || return 1
        fi
    done
    return 1
}
check_health || die "健康检查连续 3 次尝试均失败"

# 模式 4：锁文件防重复执行
LOCK_FILE="/var/run/deploy.lock"
exec 200>"$LOCK_FILE"                        # 打开文件描述符 200
if ! flock -n 200; then
    die "另一个部署进程正在运行"
fi
trap 'exec 200>&-' EXIT   # 关闭描述符释放锁；不要删除仍可能被锁定的 inode

echo "工作目录: $TEMP"

# 无论正常退出还是 exit 1，trap 都会执行

# 4. 开启 set -x 追踪一个复杂命令

NAME=alice

# 5. 写一个完整的防御性脚本骨架
cat > "$workdir/safe-script.sh" << 'EOF'
#!/bin/bash
set -euo pipefail

SCRIPT_NAME="${0##*/}"
die() { echo "[${SCRIPT_NAME}] FATAL: $*" >&2; exit 1; }
info() { echo "[${SCRIPT_NAME}] $(date '+%H:%M:%S') $*"; }

cleanup() {
    local ec=$?
    trap - EXIT
    info "清理中（退出码: $ec）..."
    if [ -n "${TEMP_DIR:-}" ]; then
        rm -rf -- "$TEMP_DIR" || printf 'cleanup failed: %s\n' "$TEMP_DIR" >&2
    fi
    exit "$ec"
}
trap cleanup EXIT

info "脚本启动"
TEMP_DIR=$(mktemp -d) || die "无法创建临时目录"
info "工作于: $TEMP_DIR"

# 你的部署逻辑写在这里
echo "Hello from safe script!"

info "脚本正常结束"
EOF
chmod +x "$workdir/safe-script.sh"
"$workdir/safe-script.sh"
rm -rf -- "$workdir"

快速自检

Q1: 开启了 set -e 的脚本，下面哪条命令失败时不会导致脚本退出？

cd /nonexistent if grep "ERROR" app.log; then echo "有错"; fi —— 其中 grep 没找到（退出码 1） tar -xzf broken.tar.gz

Q2: trap 'rm -rf "$TEMP_DIR"' EXIT 的行为是？

只在脚本正常结束时删除 TEMP_DIR Shell 走普通退出流程时执行 rm；SIGKILL 等路径不会执行 当 TEMP_DIR 变量被修改时自动执行 rm 命令

Q3: 在隔离环境中，你想先观察脚本展开后实际执行的命令，应使用什么？

在脚本里到处加 echo 语句 用 bash -x 运行脚本，追踪每条命令 把脚本重写一遍

Q4: 下面哪条命令启用了本课讨论的三个常见错误处理选项？

set -eux set -euo pipefail set -euv pipefail
