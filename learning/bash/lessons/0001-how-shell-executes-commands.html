命令是如何被执行的

Shell 的心智模型 — 你按下回车之后发生了什么

学习部署脚本时，先建立能够预测常见行为的执行模型，再记命令选项。本课区分解析、命令查找、进程、标准流和退出状态。

1. Shell 是什么

打开终端，你看到的是这样的提示符： 

cd /tmp
ls
echo hello

Shell 是命令语言解释器。下面是同步执行一条简单外部命令的入门模型；管道、后台任务、函数和内置命令会改变具体步骤。非交互式 Shell 从文件或标准输入读取命令，不显示交互提示符： 

┌─────────────────────────────────────┐
│                                     │
│  ① 打印提示符，等待你输入           │
│         ↓                           │
│  ② 解析你输入的命令                 │
│         ↓                           │
│  ③ 执行命令，等待它结束             │
│         ↓                           │
│     回到 ①                          │
│                                     │
└─────────────────────────────────────┘

当你输入 ls 并按下回车时，Shell 先解析命令，再按 Bash 的查找规则判断它是函数、内置命令还是外部可执行文件。ls 通常是外部程序；cd 则是内置命令。

对于外部命令，Shell 需要解析输入、找到程序、设置文件描述符、启动并等待进程，再取得退出状态。内置命令和函数可以直接由当前 Shell 执行。

2. Shell 怎么找到命令？

在这组入门例子中，当命令名解析为外部命令且不含斜杠时，Bash 使用 PATH 查找程序。PATH 是 Shell 变量，通常也会导出给子进程。

看看你当前的 PATH：

printf '%s\n' "$PATH"
/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin

PATH 是一串用冒号分隔的目录路径。当 Shell 看到 ls 时，它按顺序在这些目录里搜索：

  1. 先检查 /usr/local/bin/ls；若不是可执行文件，继续。
  2. 再检查 /usr/bin/ls、/bin/ls 等后续路径。
  3. 使用找到的第一个可执行文件；实际位置取决于系统和当前 PATH。

用 Bash 自带的 type -a 或 command -V 查看命令如何解析；别名会在命令查找之前展开，实际输出也可能受当前 Shell 配置影响。外部 which 工具通常只查 PATH，可能看不到函数、别名或内置命令：

type -a ls
ls is /bin/ls
command -V cd
cd is a shell builtin
PATH 是外部命令的搜索目录。当你运行 ./deploy.sh 时，斜杠告诉 Shell 不要查 PATH，直接使用该路径。当前目录通常不在 PATH 中，所以本地脚本一般写作 ./script.sh；如果脚本安装在 PATH 目录中，则可直接使用命令名。

3. 外部命令与 Shell 当前进程

在常见 Unix 实现中，Bash 启动需要等待的外部命令时，会创建子进程并在其中执行目标程序。下面的 fork + exec 是有用的简化模型，不是所有命令的固定步骤： 

  Shell 进程 (PID 1234)
       │
       │ fork()  — 创建继承大部分进程状态的子进程
       ↓
  子 Shell (PID 5678)          ← 现在有两个 Shell 进程
       │
       │ exec("ls")  — 把子进程替换成 ls 程序
       ↓
  ls 进程 (PID 5678)           ← 不再是 Shell 了，变成了 ls
       │
       │ 执行完，退出
       ↓
  Shell 进程 (PID 1234)        ← 父 Shell 一直在等待

关键点：外部程序通常在独立进程中运行；内置命令和函数可以直接在当前 Shell 中执行。cd 必须改变当前 Shell 的工作目录，因此是内置命令。管道、后台任务和子 Shell 还会引入其他进程规则，后续课程再展开。

动手试一下

在终端运行以下命令，观察进程 ID 的变化：

echo $$        # $$ 是当前 Shell 的进程 ID
1234
bash           # 启动一个子 Shell
echo $$        # 你会看到不同的 PID
5678
exit           # 退出子 Shell，回到父 Shell
echo $$        # 又变回来了
1234

4. 退出码：成功的命令和失败的命令

命令或管道完成后会产生一个整数退出状态（exit status）。Shell 把最近一个前台管道的状态放在特殊参数 $? 中；必须立即读取，否则下一条命令会覆盖它。 

ls /tmp
...（正常输出）
echo $?
0              ← 0 表示命令判定为真或成功

ls /nonexistent
ls: /nonexistent: No such file or directory
echo $?
2              ← 非 0 表示未成功，含义由命令定义
Bash 把 0 视为成功或逻辑真，非 0 视为未成功或逻辑假。具体数值由命令定义，例如 grep 返回 1 表示“没有匹配”，不一定是程序故障。if、&& 和 || 都依据这个状态决定后续动作。

这两个操作符直接利用了退出码：

make && ./deploy      # make 成功（退出码=0）才执行 deploy
make || echo "失败"    # make 失败（退出码≠0）才 echo

5. 三条数据流：stdin, stdout, stderr

按照 Unix 命令行约定，Shell 启动命令时通常让它继承三个已打开的文件描述符。程序可以关闭或重新定向它们，因此这不是“每个进程永远自带三条流”的保证：

名字 文件描述符 用途
stdin 0 标准输入 — 命令从这里读数据
stdout 1 标准输出 — 正常结果写到这里
stderr 2 标准错误 — 诊断信息通常写到这里，不保证每条内容都是错误

在常见交互式终端中，这三个描述符通常都连接到终端；从脚本、管道、IDE 或服务管理器启动时会继承不同目标。你可以继续重定向它们（这也是下一课的主题）： 

ls /tmp > files.txt       # stdout → 文件
ls /nonexistent 2> err.log # stderr → 文件
cat < input.txt            # stdin ← 文件
很多初学者以为 > 和 < 是"指向数据的流向"。更好的理解是：箭头指向数据要去的地方。ls > file 的意思是"ls 的输出 → 去 file"。

总结：你现在拥有的心智模型

每次你输入一条命令并按下回车时：

  1. Shell 按引用、运算符和语法规则读取并解析输入；它不是简单按空格切分字符串
  2. Shell 按函数、内置命令和外部命令等规则解析命令名；需要查外部程序时才搜索 PATH
  3. 内置命令可在当前 Shell 中执行；外部命令通常在子进程中加载并运行
  4. 命令通常从 stdin (fd 0) 读数据，往 stdout (fd 1) 写结果，往 stderr (fd 2) 写诊断
  5. 前台管道结束后产生一个退出状态；0 通常表示成功，具体非零含义由命令定义
  6. 交互式 Shell 再显示提示符；脚本则继续读取下一条命令

Q1: type -a python3 输出 python3 is /usr/bin/python3。这意味着什么？

python3 程序就安装在当前目录 Shell 在 PATH 的某个目录中找到了 python3 python3 是一个 Shell 内置命令

Q2: ls /tmp && echo "OK" — 什么情况下 "OK" 不会被打印？

/tmp 目录不存在 /tmp 中包含隐藏文件 /tmp 目录为空

Q3: 为什么 cd 必须是 Shell 内置命令，不能是外部程序？

因为 cd 是历史最悠久的 Unix 命令 因为外部程序无法改变父 Shell 的工作目录 因为 cd 不需要 PATH 搜索
