部署脚本常见模式

综合前 8 课知识——带适用条件的 Linux 自动化模式

本课把前 8 课的语法组合为 8 个常见模式，并明确平台、失败和恢复条件。示例用于学习 Linux 自动化，不是可以直接复制到生产环境的通用部署系统；真实服务还要处理权限、持久化数据、兼容性和业务恢复。

模式 1：结构化日志

前 8 课我们一直用 `echo`——真实的部署脚本需要更结构化的日志：时间戳、级别、输出到文件的同时不干扰 stdout 的数据流。

# 知识点回顾：函数（L6）+ 重定向（L3）+ 命令替换（L4）+ 变量（L4）

log() {
    local level="$1"; shift
    local msg="$*"
    local ts
    ts=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$ts] [$level] $msg" | tee -a "$LOG_FILE" >&2
    #                     │             │
    #                     tee→同时写文件和 stderr
    #                     LOG_FILE→来自全局配置
}

info()  { log "INFO"  "$@"; }
warn()  { log "WARN"  "$@"; }
error() { log "ERROR" "$@"; }

# 使用
info "开始部署 ${VERSION} 到 ${ENV}"
# → 屏幕和日志文件同时出现：
# [2026-07-31 14:30:01] [INFO] 开始部署 v2.0 到 production
日志三原则： ① 日志消息输出到 stderr（`>&2`），保持 stdout 通道干净给数据/返回值；② 每条日志带时间戳和级别，方便事后 grep 分析；③ 用 `tee -a` 追加（不是覆盖）写入日志文件。

模式 2：锁文件——防止并发执行

两个部署进程同时运行可能修改同一资源。Linux 常用 util-linux 的 flock 做协作式文件锁；macOS 默认没有同一命令，而且不遵守该锁的进程仍可修改资源：

# 知识点回顾：文件描述符 + trap（L8）+ die（L8）

LOCK_FILE="/var/run/deploy.lock"

# 打开一个文件描述符指向锁文件（exec 不带命令 = 在当前进程做重定向）
exec 200>"$LOCK_FILE"

# flock -n：非阻塞——拿不到锁立即失败（不排队等待）
if ! flock -n 200; then
    die "另一个部署实例正在运行（锁: $LOCK_FILE）"
fi

# 描述符关闭时内核释放锁；锁文件本身可以稳定保留
cleanup() {
    exec 200>&-
}
trap cleanup EXIT
if [ -f lock ]; then ...; touch lock 的检查与创建之间存在竞态。flock 的锁获取由内核以单次操作完成，但它是协作式锁。持锁期间不要删除锁文件：新进程可能创建并锁住同名但不同 inode，导致两组进程同时进入临界区。

模式 3：健康检查等待——服务就绪了再继续

重启服务后，下一行部署步骤可能需要服务已就绪。盲 sleep 5 秒不靠谱（可能还没好，也可能早好了白等）：

# 知识点回顾：while（L5）+ 函数（L6）+ 变量默认值（L4）+ 退出码（L1）

wait_for_http() {
    local url="${1:-http://localhost:8080/health}"
    local timeout="${2:-60}"
    local interval="${3:-2}"
    local elapsed=0

    info "等待 $url 就绪（超时: ${timeout}s）..."

    while [[ $elapsed -lt $timeout ]]; do
        if curl -sf --max-time 5 "$url" > /dev/null 2>&1; then
            info "$url 已就绪（耗时 ${elapsed}s）"
            return 0
        fi
        sleep "$interval"
        elapsed=$((elapsed + interval))
    done

    error "$url 在 ${timeout}s 内未就绪"
    return 1
}

# 使用
systemctl restart myapp
wait_for_http "http://localhost:8080/health" 120 || die "服务启动超时"

变体——等待 TCP 端口（不依赖 HTTP，通用性更强）：

wait_for_port() {
    local host="${1:-localhost}"
    local port="$2"
    local timeout="${3:-30}"
    local elapsed=0

    while [[ $elapsed -lt $timeout ]]; do
        if nc -z "$host" "$port" > /dev/null 2>&1; then
            return 0
        fi
        sleep 1
        ((elapsed++))
    done
    return 1
}

wait_for_port localhost 5432 30 || die "PostgreSQL 未就绪"

模式 4：原子操作——用临时文件 + mv 防止不完整写入

你正在写配置文件，写到一半脚本崩了——留下半个配置文件，服务下次启动直接挂掉：

# ❌ 危险：直接覆盖——写到一半崩溃会留下不完整文件
sed 's/port=80/port=8080/' config.ini > config.ini

# ✅ 安全：先写临时文件，写完了再原子替换
safe_replace() {
    local target="$1"
    local temp_file
    temp_file=$(mktemp "${target}.XXXXXX") || die "无法创建临时文件"

    # 从 stdin 读内容写到临时文件
    cat > "$temp_file" || { rm -f "$temp_file"; die "写入临时文件失败"; }

    # 备份旧内容；失败必须停止，不能假装可恢复
    if [[ -f "$target" ]]; then
        cp -p "$target" "${target}.bak" || {
            rm -f "$temp_file"
            die "备份原文件失败"
        }
    fi

    # 临时文件与目标同目录；rename 可提供原子可见性
    mv "$temp_file" "$target" || { rm -f "$temp_file"; die "替换文件失败"; }
    info "已更新: $target"
}

# 使用——通过管道传入新内容
sed 's/port=80/port=8080/' config.ini | safe_replace config.ini
当临时文件与目标位于同一文件系统，且目标是普通文件时，底层 rename 可提供原子可见性：观察者看到旧文件或新文件，而不是半截内容。这不等于崩溃后的持久性；断电保证还需要对文件和目录执行适合平台的同步操作。临时文件的模式、所有者、ACL 和扩展属性也必须按业务要求单独处理。

模式 5：备份与受控恢复

“备份命令成功”不等于“可以恢复”。备份应写到被备份目录之外；恢复先解压到隔离目录并验证，再由服务的停机和数据迁移规则决定如何切换：

# 知识点回顾：命令替换（L4）+ if/退出码（L5）+ trap（L8）+ tar（L2）

readonly APP_DIR="/opt/myapp"
readonly BACKUP_DIR="/var/backups/myapp"
BACKUP_FILE=""

backup_current() {
    mkdir -p "$BACKUP_DIR"
    BACKUP_FILE="${BACKUP_DIR}/${APP_NAME}_$(date +%Y%m%d_%H%M%S).tar.gz"
    info "创建备份: $BACKUP_FILE"
    tar -czf "$BACKUP_FILE" -C "$(dirname "$APP_DIR")" "$(basename "$APP_DIR")" \
        || die "备份失败"
}

prepare_restore() {
    [[ -f "$BACKUP_FILE" ]] || die "备份不存在: $BACKUP_FILE"
    local restore_dir
    restore_dir=$(mktemp -d "$(dirname "$APP_DIR")/.restore.XXXXXX") \
        || die "无法创建恢复目录"
    if ! tar -xzf "$BACKUP_FILE" -C "$restore_dir"; then
        rm -rf -- "$restore_dir"
        die "备份解压失败"
    fi
    local restored_app="${restore_dir}/$(basename "$APP_DIR")"
    [[ -d "$restored_app" ]] || die "备份结构无效: $restored_app"
    printf '%s\n' "$restored_app"
}

deploy() {
    backup_current
    # ... 部署步骤 ...
    if ! rsync -avz ./release/ "$APP_DIR/"; then
        local restored_app
        restored_app=$(prepare_restore)
        error "部署失败；已将备份解压到 $restored_app，验证后再按服务规则切换"
        return 1
    fi
    info "部署完成——备份保留于: $BACKUP_FILE"
}

模式 6：通知钩子

部署成功/失败时发通知——企业微信、钉钉、Slack、邮件：

# 知识点回顾：函数（L6）+ 参数展开默认值（L4）+ curl（后续课深入）

readonly WEBHOOK_URL="${DEPLOY_WEBHOOK:-}"

notify() {
    local status="$1"
    local message="$2"

    [[ -z "$WEBHOOK_URL" ]] && return 0    # 没配 webhook 就跳过
    command -v jq >/dev/null || { warn "缺少 jq，跳过通知"; return 0; }

    local payload
    payload=$(jq -n \
        --arg status "$status" --arg message "$message" \
        --arg app "$APP_NAME" --arg env "$DEPLOY_ENV" --arg time "$(date -Iseconds)" \
        '{text: ($status + ": " + $message), app: $app, environment: $env, time: $time}')

    if ! curl -fsS --connect-timeout 3 --max-time 10 \
        -X POST -H 'Content-Type: application/json' --data "$payload" "$WEBHOOK_URL" \
        >/dev/null; then
        warn "通知发送失败"
    fi
}

# 在关键节点调用
on_success() { notify "✅ 成功" "$@"; }
on_failure() { notify "❌ 失败" "$@"; }

deploy() {
    # ... 部署步骤 ...
    if deploy_new_version; then
        on_success "部署 ${VERSION} 已上线"
    else
        on_failure "部署 ${VERSION} 失败，已自动回滚"
    fi
}

模式 7：配置管理——环境变量 vs 配置文件

# 约定：调用者环境变量 > 严格 KEY=VALUE 文件 > 脚本默认值
load_config_file() {
    local file="$1" key value
    [[ -f "$file" ]] || return 0

    while IFS='=' read -r key value || [[ -n "$key" ]]; do
        [[ -z "$key" || "$key" == #* ]] && continue
        case "$key" in
            APP_NAME|DEPLOY_ENV|APP_PORT|LOG_DIR|BACKUP_RETENTION_DAYS)
                # 只在调用者尚未提供该变量时采用文件值
                [[ -v "$key" ]] || printf -v "$key" '%s' "$value"
                ;;
            *) die "配置键不受支持: $key" ;;
        esac
    done < "$file"
}

load_config_file "${APP_DIR}/config.env"
: "${APP_NAME:=myapp}"
: "${DEPLOY_ENV:=staging}"
: "${APP_PORT:=8080}"
: "${LOG_DIR:=/var/log/${APP_NAME}}"
: "${BACKUP_RETENTION_DAYS:=7}"
export APP_NAME DEPLOY_ENV APP_PORT LOG_DIR BACKUP_RETENTION_DAYS

[[ -n "$APP_NAME" && -n "$DEPLOY_ENV" ]] || die "APP_NAME 和 DEPLOY_ENV 不能为空"
info "应用: ${APP_NAME}, 环境: ${DEPLOY_ENV}, 端口: ${APP_PORT}"
source config.env 会执行文件中的任意 Shell 代码，不只是读取数据。只有文件可信且明确采用 Shell 语法时才使用它。本例故意限定为不支持转义和多行值的简单 KEY=VALUE 格式；复杂配置应使用 JSON、TOML 等格式及专用解析器。

模式 8：目录布局——结构化部署的骨架

专业的部署不会把文件散得到处都是——它们遵循一个清晰的目录布局：

/opt/myapp/                    # ← APP_HOME
├── current -> releases/v2.0   # 符号链接 → 当前版本（关键设计！）
├── releases/                  # 各版本的完整副本
│   ├── v1.0/
│   └── v2.0/
├── backups/                   # 部署前的备份
│   └── myapp_20260731.tar.gz
├── config/                    # 配置文件（独立于版本，部署不覆盖）
│   └── config.env
├── logs/                      # 日志输出（独立于版本）
│   └── deploy.log
└── shared/                    # 跨版本共享数据（uploads、cache 等）

下面把“准备新链接”和“替换当前链接”分开。示例明确依赖 GNU coreutils 的 mv -T；同目录 rename 提供原子可见性，但服务是否无停机还取决于进程重载、连接排空、数据库兼容和健康检查：

switch_link() {
    local target="$1" link="$2"
    local next_link="${link}.next.$$"
    [[ ! -e "$next_link" && ! -L "$next_link" ]] || die "临时链接已存在"
    ln -s -- "$target" "$next_link" || die "创建临时链接失败"
    mv -Tf -- "$next_link" "$link" || {
        rm -f -- "$next_link"
        die "切换链接失败"
    }
}

deploy_new_version() {
    local version="$1"
    local release_dir="${APP_HOME}/releases/${version}" current_link="${APP_HOME}/current"
    local previous=""
    [[ -L "$current_link" ]] && previous=$(readlink "$current_link")

    # 1. 部署到版本目录
    mkdir -p "$release_dir"
    rsync -avz --delete ./build/ "$release_dir/"

    # 2. 链接共享目录
    ln -sfn "${APP_HOME}/config/config.env" "${release_dir}/.env"
    ln -sfn "${APP_HOME}/logs"               "${release_dir}/logs"
    ln -sfn "${APP_HOME}/shared"             "${release_dir}/shared"

    # 3. 用新链接 + rename 替换，而不是把 ln -sfn 当作原子接口
    switch_link "$release_dir" "$current_link"
    info "已切换到版本: $version"

    # 4. 重启失败时使用调用前记录的链接，而不是猜“上一个版本”
    if ! systemctl restart myapp; then
        if [[ -n "$previous" ]]; then
            switch_link "$previous" "$current_link"
            systemctl restart myapp || error "恢复旧版本后重启仍失败"
        fi
        return 1
    fi
}
current → release 是一种有用的版本间接层：发布目录保持不可变，调用方只引用 current，旧版本也可保留用于调查和恢复。但链接替换、进程切换和业务恢复是三件不同的事，不能仅凭一次 ln -sfn 宣称原子发布或零停机。

完整骨架——把所有模式拼起来

#!/bin/bash
# deploy.sh — Linux 学习骨架；接入真实服务前必须补领域规则和测试
# 用法: ./deploy.sh  [版本号]
set -euo pipefail
IFS=$'\n\t'

# ===== 配置加载 =====
readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
: "${APP_NAME:=myapp}"          : "${DEPLOY_ENV:=staging}"
: "${APP_HOME:=/opt/${APP_NAME}}" : "${LOCK_FILE:=/var/run/deploy.lock}"
: "${LOG_FILE:=${APP_HOME}/logs/deploy.log}"

# ===== 工具函数 =====
die()  { log "FATAL" "$@"; exit 1; }
error(){ log "ERROR" "$@"; }
warn() { log "WARN"  "$@"; }
info() { log "INFO"  "$@"; }

log() {
    local level="$1"; shift
    echo "[$(date '+%H:%M:%S')] [$$] [$level] $*" | tee -a "$LOG_FILE" >&2
}

prepare_dirs() {
    mkdir -p "${APP_HOME}/releases" "${APP_HOME}/backups" "${APP_HOME}/logs" \
        || die "无法创建部署目录"
}

# ===== 锁 =====
acquire_lock() {
    exec 200>"$LOCK_FILE"
    flock -n 200 || die "另一个部署实例正在运行"
}

wait_for_http() {
    local url="$1" timeout="$2" started=$SECONDS
    while (( SECONDS - started < timeout )); do
        curl -fsS --connect-timeout 2 --max-time 5 "$url" >/dev/null && return 0
        sleep 2
    done
    return 1
}

switch_link() {
    local target="$1" link="$2" next_link="${2}.next.$$"
    ln -s -- "$target" "$next_link" || return 1
    mv -Tf -- "$next_link" "$link" || {
        rm -f -- "$next_link"
        return 1
    }
}

# ===== 部署 =====
deploy() {
    local version="${1:-latest}"

    info "开始部署 ${version} 到 ${DEPLOY_ENV}"
    local release_dir="${APP_HOME}/releases/${version}"
    local current_link="${APP_HOME}/current" previous=""
    [[ -L "$current_link" ]] && previous=$(readlink "$current_link")
    mkdir -p "$release_dir"

    # 备份
    if [[ -L "$current_link" ]]; then
        tar -chzf "${APP_HOME}/backups/$(date +%Y%m%d_%H%M%S).tar.gz" \
            -C "$APP_HOME" current || die "备份失败"
    fi

    # 部署文件 + 同目录 rename 切换（依赖 GNU mv -T）
    rsync -avz "${SCRIPT_DIR}/build/" "$release_dir/"
    switch_link "$release_dir" "$current_link" || die "版本链接切换失败"

    # 重启 + 等待就绪
    if ! systemctl restart "$APP_NAME" \
        || ! wait_for_http "http://localhost:${APP_PORT:-8080}/health" 60; then
        if [[ -n "$previous" ]]; then
            switch_link "$previous" "$current_link" \
                && systemctl restart "$APP_NAME" \
                || error "恢复旧链接或重启失败"
        fi
        die "新版本未通过启动检查"
    fi

    info "✅ 部署完成"
}

# ===== 主入口 =====
main() {
    prepare_dirs
    acquire_lock
    trap 'info "脚本退出 (exit=$?)"' EXIT

    local env="${1:-}"; local version="${2:-$(date +%Y%m%d%H%M%S)}"
    [[ "$env" =~ ^(staging|production)$ ]] || die "无效环境: $env"
    DEPLOY_ENV="$env"

    deploy "$version"
}
main "$@"

快速自检

Q1: 为什么用 `mktemp` + `mv` 写配置文件，而不直接 `sed -i`？

mktemp 创建的文件名有随机后缀，防止被其他进程猜到 先写临时文件再 mv 原子替换——中途崩溃不会留下半截文件 mktemp 会自动加密临时文件

Q2: current -> releases/v2 这一版本间接层的主要价值是？

节省磁盘空间——只有一个版本的文件 调用方使用稳定路径，发布目录可保持不可变，并能保留旧版本 符号链接比实际文件读写速度快

Q3: 部署脚本里 `flock -n` 的 `-n` 参数是什么意思？

新建锁文件（new file） 非阻塞——拿不到锁立即失败，不排队等待 不创建文件（no file），只检查锁是否存在

Q4: 在 `wait_for_http` 函数中，为什么 `curl` 的输出要重定向到 `/dev/null`？

因为只关心退出码（服务是否响应），不关心响应体内容 因为 curl 的输出会干扰 bash 脚本的执行流 因为 /dev/null 会自动缓存响应，加速下一次检查
