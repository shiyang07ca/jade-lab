部署脚本常见模式

综合前 8 课知识——带适用条件的 Linux 自动化模式

本课把前 8 课的语法组合为 8 个常见模式，并明确平台、失败和恢复条件。示例用于学习 Linux 自动化，不是可以直接复制到生产环境的通用部署系统；真实服务还要处理权限、持久化数据、兼容性和业务恢复。

模式 1：可解析的文本日志

自动化脚本至少需要稳定的文本格式：时间戳、级别和消息写入 stderr，并按明确策略追加到文件。这仍不是 JSON 等结构化日志；字段中若允许换行，还要先定义转义规则。

# 知识点回顾：函数（L6）+ 重定向（L3）+ 命令替换（L4）+ 变量（L4）

log() {
    local level="$1"; shift
    local msg="$*"
    local ts
    ts=$(date '+%Y-%m-%d %H:%M:%S')
    local line="[$ts] [$level] $msg"
    printf '%s\n' "$line" >&2
    printf '%s\n' "$line" >> "$LOG_FILE"  # 文件写入失败时返回非零
}

info()  { log "INFO"  "$@"; }
warn()  { log "WARN"  "$@"; }
error() { log "ERROR" "$@"; }

# 使用
info "开始部署 ${VERSION} 到 ${ENV}"
# → 屏幕和日志文件同时出现：
# [2026-07-31 14:30:01] [INFO] 开始部署 v2.0 到 production
先定义三件事：① stdout 是否保留给机器可读数据；② 日志文件写失败是否导致任务失败；③ 消息里的换行、敏感值和并发写入如何处理。本例把日志写 stderr 和文件，并把文件写入失败暴露给调用者。

模式 2：锁文件——防止并发执行

两个部署进程同时运行可能修改同一资源。Linux 常用 util-linux 的 flock 做协作式文件锁；macOS 默认没有同一命令，而且不遵守该锁的进程仍可修改资源：

# 知识点回顾：文件描述符 + trap（L8）+ die（L8）

LOCK_FILE="/var/run/deploy.lock"

# 打开一个文件描述符指向锁文件（exec 不带命令 = 在当前进程做重定向）
exec 200>"$LOCK_FILE"

# flock -n：非阻塞——拿不到锁立即失败（不排队等待）
if ! flock -n 200; then
    die "另一个部署实例正在运行（锁: $LOCK_FILE）"
fi

# 描述符关闭时内核释放锁；锁文件本身可以稳定保留
cleanup() {
    exec 200>&-
}
trap cleanup EXIT
if [ -f lock ]; then ...; touch lock 的检查与创建之间存在竞态。flock 的锁获取由内核以单次操作完成，但它是协作式锁。持锁期间不要删除锁文件：新进程可能创建并锁住同名但不同 inode，导致两组进程同时进入临界区。

模式 3：健康检查等待——服务就绪了再继续

重启服务后，下一行部署步骤可能需要服务已就绪。盲 sleep 5 秒不靠谱（可能还没好，也可能早好了白等）：

# 知识点回顾：while（L5）+ 函数（L6）+ 变量默认值（L4）+ 退出码（L1）

wait_for_http() {
    local url="${1:-http://localhost:8080/health}"
    local timeout="${2:-60}"
    local interval="${3:-2}"
    local started=$SECONDS

    case "$url" in
        http://*|https://*) ;;
        *) error "健康检查只接受 http/https URL: $url"; return 2 ;;
    esac
    [[ "$timeout" =~ ^[1-9][0-9]{0,5}$ ]] \
        || { error "timeout 必须是 1..999999 的整数秒"; return 2; }
    [[ "$interval" =~ ^([1-9][0-9]{0,3}(\.[0-9]+)?|0\.[0-9]*[1-9][0-9]*)$ ]] \
        || { error "interval 必须是正秒数"; return 2; }

    info "等待 $url 就绪（超时: ${timeout}s）..." || return 1

    while (( SECONDS - started < timeout )); do
        if curl -fsS --connect-timeout 2 --max-time 5 --url "$url" > /dev/null; then
            info "$url 已就绪（耗时 $((SECONDS - started))s）" || return 1
            return 0
        fi
        sleep "$interval" || { error "健康检查等待被中断"; return 1; }
    done

    error "$url 在 ${timeout}s 内未就绪"
    return 1
}

# 使用
systemctl restart myapp || die "服务重启失败"
wait_for_http "http://localhost:8080/health" 120 || die "服务启动超时"
这里的 timeout 限制何时开始下一次尝试，不是严格墙钟期限。一次已开始的 curl 最多还会运行 5 秒，随后 sleep 也可能越过边界；需要严格截止时间时，应按剩余时间缩短单次请求和等待。

变体——等待 TCP 端口。连接成功只证明端口接受连接，不证明数据库已完成恢复、认证可用或应用已经就绪：

wait_for_port() {
    local host="${1:-localhost}"
    local port="$2"
    local timeout="${3:-30}"
    local elapsed=0

    [[ -n "$host" && "$host" != -* ]] \
        || { error "host 不能为空或以 - 开头"; return 2; }
    [[ "$port" =~ ^[0-9]{1,5}$ ]] && (( 10#$port >= 1 && 10#$port <= 65535 )) \
        || { error "port 必须是 1..65535"; return 2; }
    [[ "$timeout" =~ ^[1-9][0-9]{0,5}$ ]] \
        || { error "timeout 必须是 1..999999 的整数秒"; return 2; }

    while [[ $elapsed -lt $timeout ]]; do
        if nc -z "$host" "$port" > /dev/null 2>&1; then
            return 0
        fi
        sleep 1 || { error "端口等待被中断"; return 1; }
        ((elapsed += 1))
    done
    return 1
}

wait_for_port localhost 5432 30 || die "PostgreSQL 未就绪"

模式 4：原子操作——用临时文件 + mv 防止不完整写入

你正在写配置文件，写到一半脚本崩了——留下半个配置文件，服务下次启动直接挂掉：

# ❌ 危险：直接覆盖——写到一半崩溃会留下不完整文件
sed 's/port=80/port=8080/' config.ini > config.ini

# ✅ 先验证目标，再在同目录生成完整的新文件
replace_port() {
    local target="$1"
    local temp_file
    [[ -f "$target" && ! -L "$target" ]] || die "目标必须是普通文件: $target"
    temp_file=$(mktemp "${target}.XXXXXX") || die "无法创建临时文件"

    # 直接检查转换命令；不要用 producer | safe_replace 隐藏上游失败
    if ! sed 's/port=80/port=8080/g' "$target" > "$temp_file"; then
        rm -f -- "$temp_file"
        die "生成新配置失败"
    fi

    # 本例限定 GNU chmod；所有者、ACL、xattr 仍需项目单独定义
    chmod --reference="$target" "$temp_file" || {
        rm -f -- "$temp_file"
        die "复制文件模式失败"
    }
    cp -p -- "$target" "${target}.bak" || {
        rm -f -- "$temp_file"
        die "备份原文件失败"
    }

    # 临时文件与目标同目录；rename 可提供原子可见性
    mv -f -- "$temp_file" "$target" || {
        rm -f -- "$temp_file"
        die "替换文件失败"
    }
    info "已更新: $target"
}

replace_port config.ini
当临时文件与目标位于同一文件系统，且目标是普通文件时，底层 rename 可提供原子可见性：观察者看到旧文件或新文件，而不是半截内容。这不等于崩溃后的持久性；断电保证还需要对文件和目录执行适合平台的同步操作。临时文件的模式、所有者、ACL 和扩展属性也必须按业务要求单独处理。
本例还假定目标目录只由可信主体写入。检查目标后再创建临时文件和替换仍存在路径竞态； 在共享或攻击者可写目录中，应使用目录文件描述符等更强的系统接口，而不是继续扩展 Shell 片段。

模式 5：备份与受控恢复

“备份命令成功”不等于“可以恢复”。备份应写到被备份目录之外；恢复先解压到隔离目录并验证， 再由服务的停机和数据迁移规则决定如何切换。示例只恢复本流程生成且访问控制可信的归档； 外部归档还必须检查成员路径、链接及所有权等安全边界：

# 知识点回顾：命令替换（L4）+ if/退出码（L5）+ trap（L8）+ tar（L2）

readonly APP_DIR="/opt/myapp"
readonly BACKUP_DIR="/var/backups/myapp"
BACKUP_FILE=""

backup_current() {
    local timestamp app_parent app_name
    timestamp=$(date +%Y%m%d_%H%M%S) || die "无法生成备份时间"
    app_parent=$(dirname "$APP_DIR") || die "无法确定应用父目录"
    app_name=$(basename "$APP_DIR") || die "无法确定应用目录名"
    mkdir -p "$BACKUP_DIR" || die "无法创建备份目录: $BACKUP_DIR"
    BACKUP_FILE="${BACKUP_DIR}/${APP_NAME}_${timestamp}.tar.gz"
    info "创建备份: $BACKUP_FILE" || die "无法写入备份日志"
    tar -czf "$BACKUP_FILE" -C "$app_parent" "$app_name" \
        || die "备份失败"
}

prepare_restore() {
    [[ -f "$BACKUP_FILE" ]] || die "备份不存在: $BACKUP_FILE"
    local app_parent restore_dir
    app_parent=$(dirname "$APP_DIR") || die "无法确定应用父目录"
    restore_dir=$(mktemp -d "${app_parent}/.restore.XXXXXX") \
        || die "无法创建恢复目录"
    if ! tar -xzf "$BACKUP_FILE" -C "$restore_dir"; then
        rm -rf -- "$restore_dir"
        die "备份解压失败"
    fi
    local app_name restored_app
    app_name=$(basename "$APP_DIR") || {
        rm -rf -- "$restore_dir"
        die "无法确定应用目录名"
    }
    restored_app="${restore_dir}/${app_name}"
    if [[ ! -d "$restored_app" ]]; then
        rm -rf -- "$restore_dir"
        die "备份结构无效: $restored_app"
    fi
    printf '%s\n' "$restored_app"
}

deploy() {
    backup_current
    # ... 部署步骤 ...
    if ! rsync -avz ./release/ "$APP_DIR/"; then
        local restored_app
        restored_app=$(prepare_restore) || {
            error "部署失败，且无法准备恢复目录"
            return 1
        }
        error "部署失败；已将备份解压到 $restored_app，验证后再按服务规则切换"
        return 1
    fi
    info "部署完成——备份保留于: $BACKUP_FILE"
}

模式 6：通知钩子

部署成功/失败时发通知——企业微信、钉钉、Slack、邮件：

# 知识点回顾：函数（L6）+ 参数展开默认值（L4）+ curl（后续课深入）

readonly WEBHOOK_URL="${DEPLOY_WEBHOOK:-}"

notify() {
    local status="$1"
    local message="$2"

    [[ -z "$WEBHOOK_URL" ]] && return 0    # 没配 webhook 就跳过
    command -v jq >/dev/null || { warn "缺少 jq，跳过通知"; return 0; }
    case "$WEBHOOK_URL" in
        http://*|https://*) ;;
        *) warn "webhook 只接受 http/https URL"; return 0 ;;
    esac

    local timestamp payload
    timestamp=$(date -u '+%Y-%m-%dT%H:%M:%SZ') \
        || { warn "无法生成通知时间"; return 0; }
    payload=$(jq -n \
        --arg status "$status" --arg message "$message" \
        --arg app "$APP_NAME" --arg env "$DEPLOY_ENV" --arg time "$timestamp" \
        '{text: ($status + ": " + $message), app: $app, environment: $env, time: $time}') \
        || { warn "无法构造通知 JSON"; return 0; }

    if ! curl -fsS --connect-timeout 3 --max-time 10 \
        --proto '=http,https' --header 'Content-Type: application/json' \
        --data-binary "$payload" --url "$WEBHOOK_URL" \
        >/dev/null; then
        warn "通知发送失败"
    fi
    return 0
}

# 在关键节点调用
on_success() { notify "✅ 成功" "$@"; }
on_failure() { notify "❌ 失败" "$@"; }

deploy() {
    # ... 部署步骤 ...
    if deploy_new_version; then
        on_success "部署 ${VERSION} 已上线"
    else
        on_failure "部署 ${VERSION} 失败；请查看恢复状态和日志"
    fi
}

模式 7：配置管理——环境变量 vs 配置文件

# 约定：调用者环境变量 > 严格 KEY=VALUE 文件 > 脚本默认值
load_config_file() {
    local file="$1" key value
    [[ -f "$file" ]] || return 0

    while IFS='=' read -r key value || [[ -n "$key" ]]; do
        [[ -z "$key" || "$key" == \#* ]] && continue
        case "$key" in
            APP_NAME|DEPLOY_ENV|APP_PORT|LOG_DIR|BACKUP_RETENTION_DAYS)
                # 只在调用者尚未提供该变量时采用文件值
                [[ -v "$key" ]] || printf -v "$key" '%s' "$value"
                ;;
            *) die "配置键不受支持: $key" ;;
        esac
    done < "$file"
}

load_config_file "${APP_DIR}/config.env"
: "${APP_NAME:=myapp}"
: "${DEPLOY_ENV:=staging}"
: "${APP_PORT:=8080}"
: "${LOG_DIR:=/var/log/${APP_NAME}}"
: "${BACKUP_RETENTION_DAYS:=7}"
export APP_NAME DEPLOY_ENV APP_PORT LOG_DIR BACKUP_RETENTION_DAYS

[[ -n "$APP_NAME" && -n "$DEPLOY_ENV" ]] || die "APP_NAME 和 DEPLOY_ENV 不能为空"
[[ "$APP_NAME" =~ ^[A-Za-z0-9._-]+$ ]] || die "APP_NAME 格式无效"
[[ "$APP_PORT" =~ ^[0-9]{1,5}$ ]] \
    && (( 10#$APP_PORT >= 1 && 10#$APP_PORT <= 65535 )) \
    || die "APP_PORT 必须是 1..65535"
[[ "$BACKUP_RETENTION_DAYS" =~ ^(0|[1-9][0-9]{0,4})$ ]] \
    || die "BACKUP_RETENTION_DAYS 必须是 0..99999"
info "应用: ${APP_NAME}, 环境: ${DEPLOY_ENV}, 端口: ${APP_PORT}"
source config.env 会执行文件中的任意 Shell 代码，不只是读取数据。只有文件可信且明确采用 Shell 语法时才使用它。本例故意限定为不支持转义和多行值的简单 KEY=VALUE 格式；复杂配置应使用 JSON、TOML 等格式及专用解析器。

模式 8：目录布局——结构化部署的骨架

目录应区分不可变发布、共享配置、运行数据和外部备份。下面只是传统 Linux 服务的一种布局，容器和编排平台会采用不同边界：

/opt/myapp/                    # ← APP_HOME
├── current -> releases/v2.0   # 符号链接 → 当前版本（关键设计！）
├── releases/                  # 各版本的完整副本
│   ├── v1.0/
│   └── v2.0/
├── config/                    # 配置文件（独立于版本，部署不覆盖）
│   └── config.env
├── logs/                      # 日志输出（独立于版本）
│   └── deploy.log
└── shared/                    # 跨版本共享数据（是否备份需单独定义）

/var/backups/myapp/            # 放在 APP_HOME 外，避免随目标一起损坏

下面把“准备新链接”和“替换当前链接”分开。示例明确依赖 GNU coreutils 的 mv -T；同目录 rename 提供原子可见性，但服务是否无停机还取决于进程重载、连接排空、数据库兼容和健康检查：

switch_link() {
    local target="$1" link="$2"
    local next_link="${link}.next.$$"
    if [[ -e "$next_link" || -L "$next_link" ]]; then
        error "临时链接已存在: $next_link"
        return 1
    fi
    if ! ln -s -- "$target" "$next_link"; then
        error "创建临时链接失败: $next_link"
        return 1
    fi
    if ! mv -Tf -- "$next_link" "$link"; then
        rm -f -- "$next_link"
        error "切换链接失败: $link"
        return 1
    fi
}

deploy_new_version() {
    local version="$1"
    local release_dir="${APP_HOME}/releases/${version}" current_link="${APP_HOME}/current"
    local previous=""

    # 1. 版本标识必须先通过项目规则校验，发布目录不得复用
    [[ "$version" =~ ^[A-Za-z0-9._-]+$ ]] \
        || { error "无效版本标识: $version"; return 2; }
    if [[ -L "$current_link" ]]; then
        previous=$(readlink "$current_link") \
            || { error "无法读取当前版本链接"; return 1; }
    fi
    [[ ! -e "$release_dir" ]] \
        || { error "发布目录已存在: $release_dir"; return 1; }
    mkdir -p "$release_dir" \
        || { error "无法创建发布目录: $release_dir"; return 1; }
    rsync -avz --delete ./build/ "$release_dir/" \
        || { error "复制发布文件失败；保留目录供检查: $release_dir"; return 1; }

    # 2. 链接共享目录
    ln -sfn "${APP_HOME}/config/config.env" "${release_dir}/.env" \
        || { error "无法链接配置"; return 1; }
    ln -sfn "${APP_HOME}/logs" "${release_dir}/logs" \
        || { error "无法链接日志目录"; return 1; }
    ln -sfn "${APP_HOME}/shared" "${release_dir}/shared" \
        || { error "无法链接共享目录"; return 1; }

    # 3. 用新链接 + rename 替换，而不是把 ln -sfn 当作原子接口
    switch_link "$release_dir" "$current_link" || return 1

    # 4. 重启失败时使用调用前记录的链接，而不是猜“上一个版本”
    if ! systemctl restart myapp; then
        error "新版本重启失败: $version"
        if [[ -n "$previous" ]]; then
            switch_link "$previous" "$current_link" || return 1
            if ! systemctl restart myapp; then
                error "恢复旧版本后重启仍失败"
                return 1
            fi
        else
            error "没有可恢复的旧版本链接"
        fi
        return 1
    fi
    info "已切换并启动版本: $version" || printf '%s\n' "部署成功，但写日志失败" >&2
    return 0
}
current → release 是一种有用的版本间接层：发布目录保持不可变，调用方只引用 current，旧版本也可保留用于调查和恢复。但链接替换、进程切换和业务恢复是三件不同的事，不能仅凭一次 ln -sfn 宣称原子发布或零停机。

动手练习（5 分钟）

在 GNU mv 环境体验同目录链接替换；练习使用唯一临时目录，退出时自动清理。如果命令不支持 -T，先停止并查本机手册：

# 1. 模拟先创建新链接、再通过 rename 替换
(
set -e
DEMO_DIR=$(mktemp -d)
trap 'rm -rf -- "$DEMO_DIR"' EXIT
mkdir -p "$DEMO_DIR"/releases/{v1,v2}
printf '%s\n' "v1 content" > "$DEMO_DIR/releases/v1/index.html"
printf '%s\n' "v2 content" > "$DEMO_DIR/releases/v2/index.html"
ln -s "$DEMO_DIR/releases/v1" "$DEMO_DIR/current.next"
mv -Tf "$DEMO_DIR/current.next" "$DEMO_DIR/current"
cat "$DEMO_DIR/current/index.html"   # → v1 content
ln -s "$DEMO_DIR/releases/v2" "$DEMO_DIR/current.next"
mv -Tf "$DEMO_DIR/current.next" "$DEMO_DIR/current"
cat "$DEMO_DIR/current/index.html"   # → v2 content

# 2. 体验原子写入——先写临时文件再 mv
printf '%s\n' "new config" > "$DEMO_DIR/config.tmp" \
    && mv "$DEMO_DIR/config.tmp" "$DEMO_DIR/config.ini" \
    && echo "原子写入完成"

# 3. 模拟健康检查等待模式
cat > "$DEMO_DIR/health-check.sh" << 'EOF'
#!/bin/bash
set -u
wait_for_file() {
    local file="$1"; local timeout="${2:-10}"; local elapsed=0
    echo "等待 $file 出现..."
    while [[ $elapsed -lt $timeout ]]; do
        if [[ -f "$file" ]]; then
            echo "✅ 文件已出现！耗时 ${elapsed}s"
            return 0
        fi
        sleep 1
        ((elapsed += 1))
    done
    echo "❌ 超时" >&2; return 1
}
ready_file="$1"
wait_for_file "$ready_file" 10 &
bg_pid=$!
echo "模拟 3 秒后创建标记文件..."
sleep 3
touch -- "$ready_file"
wait "$bg_pid"
EOF
bash "$DEMO_DIR/health-check.sh" "$DEMO_DIR/health-ready"
)

接入真实服务前的验证清单

不要把八种模式机械拼成一个大脚本。先为目标服务逐项回答并测试：

  • 输入：环境、版本和路径允许哪些值，谁负责验证？
  • 并发：哪些资源需要互斥，所有写入者是否使用同一种锁？
  • 发布：哪些目录不可变，配置、密钥和持久化数据由谁管理？
  • 就绪：HTTP 成功是否足够，是否还要验证响应字段和依赖状态？
  • 失败：每一步失败后停止、清理还是恢复；恢复失败如何报告？
  • 证据：成功、超时、信号中断、磁盘写满和并发运行是否有自动测试？

快速自检

Q1: 为什么用 `mktemp` + `mv` 写配置文件，而不直接 `sed -i`？

mktemp 创建的文件名有随机后缀，防止被其他进程猜到 先写临时文件再 mv 原子替换——中途崩溃不会留下半截文件 mktemp 会自动加密临时文件

Q2: current -> releases/v2 这一版本间接层的主要价值是？

节省磁盘空间——只有一个版本的文件 调用方使用稳定路径，发布目录可保持不可变，并能保留旧版本 符号链接比实际文件读写速度快

Q3: 部署脚本里 `flock -n` 的 `-n` 参数是什么意思？

新建锁文件（new file） 非阻塞——拿不到锁立即失败，不排队等待 不创建文件（no file），只检查锁是否存在

Q4: 在本例 `wait_for_http` 中，为什么把 curl 的响应体重定向到 /dev/null？

因为只关心退出码（服务是否响应），不关心响应体内容 因为 curl 的输出会干扰 bash 脚本的执行流 因为 /dev/null 会自动缓存响应，加速下一次检查
